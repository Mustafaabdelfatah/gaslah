## 1. نظرة عامة

هذا المجال يغطّي كل حركة نقود تلمس العميل أو المنشأة أو المنصّة، عبر خمس منظومات مترابطة:

1. **المحفظة (Wallet):** رصيد مدفوع مسبقاً لكل عميل، مصدر الحقيقة الوحيد لحركته هو `WalletService`
   (شحن/سحب/استرجاع) بقفل صفّي على العميل — يمنع الصرف المزدوج وفقدان التحديث.

2. **الدفع الأونلاين (Online payment):** بوابة دفع إلكتروني (Moyasar في الإنتاج، Stub محلياً،
   Unavailable إذا نقص الإعداد). ثلاث نقاط دخول تسجّل مدفوعات: نقطة البيع POS، صفحة تفاصيل الطلب،
   وصفحة الدفع العامة (روابط الدفع). الأخيرة فقط تمرّ عبر بوابة على حساب المنصّة.

3. **رابط الدفع (Payment link):** توكن موقّع بلا حالة (`PayToken`) يُصدره موظف لطلب غير مدفوع؛ يفتحه
   العميل بلا تسجيل دخول، والمبلغ يُعاد حسابه خادمياً دائماً من الطلب.

4. **الويبهوك (Webhook):** المسار الوحيد الذي لا يعتمد على بقاء متصفّح العميل بعد إعادة التوجيه —
   Moyasar تناديه بسرّ مشترك، وهو يسوّي الطلب مرّة واحدة فقط (بمفتاح idempotency مشترك مع صفحة الدفع).

5. **التسويات البنكية (Payout settlements):** الأموال التي حصّلتها غسلة على حساب بوابتها نيابةً عن
   المنشأة (روابط الدفع / بوّابة العميل) تُجمَّع في دفعات وتُحوَّل بنكياً للمنشأة بعد موافقة متعددة
   (maker-checker: N أصوات أدمن مميّزة، والمُنشئ لا يصوّت).

بالإضافة إلى **سجلات المنصّة**: سجل المدفوعات عبر كل المنشآت (`OnlineCharge`)، وسجل مبيعات المنصّة
(اشتراكات + شحنات SUBSCRIPTION).

**فصل الأدوار في تدفّق الفلوس:**
- مدفوعات POS/تفاصيل الطلب النقدية أو بالبطاقة اليدوية → تسقط في درج المنشأة مباشرة (لا تسوية).
- مدفوعات رابط الدفع / بوّابة العميل عبر البوّابة (`viaGateway = true`) → تُحصَّل على حساب **المنصّة**،
  وتدخل **بركة التسويات غير المسوّاة**، لتُحوَّل لاحقاً بنكياً للمنشأة بعد خصم رسوم المنصّة.

## 2. الكيانات

### 2.1 Payment — دفعة على طلب

جدول `Payment` (Prisma، فيه `createdAt` فقط بلا `updatedAt`؛ الموديل يُعطِّل عمود التحديث).

| الحقل | المعنى |
|---|---|
| `id` | معرّف cuid نصّي (مفتاح أساسي غير تزايدي). |
| `orderId` | الطلب الذي تخصّه الدفعة. |
| `method` | طريقة الدفع — enum بوستجرس `PaymentMethod`. |
| `amount` | المبلغ المُحصَّل (float، مقرّب لخانتين). |
| `reference` | مرجع نصّي: للبوابة يساوي `gateway:{txnId}` وهو مفتاح idempotency؛ لليدوي مرجع حرّ اختياري. |
| `verifyMode` | وضع التحقق (يُملأ للبطاقة/التحويل اليدوي فقط: `CARD`/`TRANSFER`). |
| `shiftId` | الوردية التي حصّلت الدفعة (لمطابقة الدرج). |
| `viaGateway` | `true` ⇒ حُصِّلت على حساب بوّابة المنصّة ⇒ تدخل بركة التسويات. `false`/null ⇒ درج المنشأة. |
| `settlementId` | معرّف دفعة التسوية التي حجزت هذه الدفعة (null = غير مسوّاة بعد). |
| `createdAt` | وقت الإنشاء. |

**enum `PaymentMethod`** (لا يُضاف له قيم — قيد صارم):
`CASH` (نقدي) · `CARD` (بطاقة) · `TRANSFER` (تحويل بنكي يدوي) · `WALLET` (خصم من المحفظة) ·
`DEFERRED` (آجل — علامة حالة لا تحصيل، بلا صفّ Payment ولا قيد).

> ملاحظة: الدفعات الآجلة (`DEFERRED`) في تفاصيل الطلب لا تنشئ صفّ Payment إطلاقاً — تُعلِّم حالة الطلب فقط.

### 2.2 WalletTransaction — صفّ دفتر لحركة محفظة واحدة

جدول `WalletTransaction` (`createdAt` فقط، `timestamps = false`).

| الحقل | المعنى |
|---|---|
| `id` | cuid. |
| `customerId` | العميل صاحب المحفظة. |
| `type` | نوع الحركة — انظر enum أدناه. |
| `amount` | مبلغ الحركة (موجب دائماً؛ الاتجاه يحدّده `type`). |
| `balanceAfter` | الرصيد الجاري بعد الحركة — يُكتب داخل نفس المعاملة تحت القفل، فلا ينحرف عن الرصيد المخزَّن. |
| `refId` | ربط المصدر: طلب (`order.id`) / استرجاع (`order.id`) / استبدال ولاء (`account.id`) / null للشحن اليدوي. |
| `note` | وصف بشري بالعربي. |
| `createdAt` | وقت الحركة. |

**enum `type` (نوع حركة المحفظة):**
- **`TOPUP`** — شحن/إيداع: شحن يدوي، فائض دفع نقدي يتحوّل رصيداً، استبدال نقاط ولاء برصيد. الوحيد الذي
  يَنشر قيداً محاسبياً (Dr نقد/بنك / Cr إيراد مؤجَّل) عند `postAccounting = true`.
- **`DEBIT`** — سحب/صرف: دفع سلة أو سداد طلب من الرصيد. يُحرَسه فحص كفاية الرصيد على القيمة **المقفولة**.
- **`REFUND`** — استرجاع: إعادة رصيد عند إلغاء سلّة دُفعت من المحفظة. يُستدعى بـ `postAccounting = false`
  لأن القيد الصحيح (استعادة الالتزام المؤجَّل) يُنشَر يدوياً في نقطة الاستدعاء لا كشحن نقدي.

> `balanceAfter` و`refId` ونمط القفل مطابقان لنمط §4.1 في ملف 00.

### 2.3 OnlineCharge — دفتر الشحنات الإلكترونية (مرآة البوابة)

جدول `OnlineCharge` (فيه `createdAt` و`updatedAt`).

| الحقل | المعنى |
|---|---|
| `id` | cuid. |
| `orgId` | المنشأة المالكة (تُشتقّ من فرع الطلب). |
| `provider` | مزوّد البوابة: `moyasar` / `stub` (أو `services.payment.driver`). |
| `providerRef` | معرّف عملية المزوّد (نفسه `txnId`). |
| `purpose` | غرض الشحنة — انظر enum أدناه. |
| `orderId` | الطلب المرتبط (لشحنات الدفع). |
| `customerId` | العميل. |
| `subscriptionId` | الاشتراك (لشحنات الاشتراك — تُدار في مجال الاشتراكات). |
| `amount` | المبلغ. |
| `currency` | العملة (SAR). |
| `status` | حالة الشحنة — انظر enum أدناه. |
| `idempotencyKey` | يعيد استخدام `Payment.reference` (`gateway:{txnId}`) — فريد لكل عملية مزوّد، ومفتاح إزالة التكرار الذي يعتمده الويبهوك. |
| `rawStatus` | الحالة الخام كما وردت من المزوّد (`paid`/`refunded`…). |

**enum `status` (حالة الشحنة):** `INITIATED` (بُدئت) · `PAID` (مدفوعة) · `FAILED` (فشلت) · `REFUNDED` (مُستردَّة).

**enum `purpose` (الغرض):** `ORDER_PAYMENT` (دفع طلب — يُنشأ في هذا المجال) · `SUBSCRIPTION` (دفع اشتراك
منصّة — يُنشأ في مجال الاشتراكات ويُقرأ في سجل المبيعات). شحنات الأجهزة/الاشتراك تحمل metadata مختلفة
ويسوّيها تدفقها الخاص (الويبهوك يتجاهلها كطلب).

> لماذا `OnlineCharge` بجانب `Payment`؟ لأن `Payment.method` محصور في enum ضيّق ويفقد المزوّد ومعرّف
> العملية والعملة وحالة التسوية؛ ولأن **مراقب مدفوعات المنصّة يقرأ `OnlineCharge` حصرياً** — طلب دُفِع
> عبر البوّابة بلا صفّ `OnlineCharge` لم يكن ليظهر في المراقب.

### 2.4 PayoutSettlement — دفعة تسوية بنكية

جدول `PayoutSettlement` (فيه `createdAt` و`updatedAt`).

| الحقل | المعنى |
|---|---|
| `id` | cuid. |
| `orgId` | المنشأة المستفيدة. |
| `status` | حالة الدفعة — آلة الحالات §6.4. |
| `urgent` | `true` إذا كانت طلباً عاجلاً من المنشأة (لا انتظار للجدولة). |
| `periodStart` / `periodEnd` | أقدم/أحدث `createdAt` بين مدفوعات الدفعة (الفترة المُغطّاة). |
| `paymentCount` | عدد المدفوعات المحجوزة في الدفعة. |
| `grossAmount` | إجمالي المدفوعات (قبل الرسوم). |
| `feeAmount` | رسوم التحويل التي تخصمها المنصّة (≤ الإجمالي، ≥ 0). |
| `netAmount` | الصافي المُحوَّل = الإجمالي − الرسوم. |
| `currency` | العملة (SAR). |
| `bankSnapshot` | لقطة بيانات بنك المنشأة وقت الإنشاء (iban/bankName/beneficiary) — تُخفَّى لغير مُنفِّذ التحويل. |
| `requestedById` | مالك المنشأة الذي طلب التسوية العاجلة (إن وُجد). |
| `createdById` | الأدمن (المنصّة) الذي أنشأ الدفعة — لا يحقّ له التصويت عليها (maker-checker). |
| `approvedAt` | وقت اكتمال الموافقات. |
| `sentById` / `sentAt` | مَن سجّل التحويل ومتى. |
| `transferRef` | رقم الحوالة البنكية عند markSent. |
| `note` | ملاحظة إنشاء. |
| `rejectedReason` | سبب الرفض. |

**enum `status` (حالة التسوية):**
`PENDING_APPROVAL` (قيد الموافقة) · `APPROVED` (مُوافَق عليها) · `SENT` (مُحوَّلة) ·
`REJECTED` (مرفوضة) · `CANCELLED` (مُلغاة).
الحالتان المفتوحتان (`OPEN_STATUSES`) = `PENDING_APPROVAL` + `APPROVED`.

| الحقل | المعنى |

| `adminId` | الأدمن المُصوِّت. |

## 3. المحفظة (Wallet)

### 3.1 مصدر الحقيقة الوحيد: WalletService

كل حركة محفظة (شحن/سحب/استرجاع) **يجب** أن تمرّ عبر `WalletService::credit` أو `::debit`. لا يُقرأ
`walletBalance` من الموديل ويُكتب يدوياً في أي مكان (خطر فقدان التحديث / الصرف المزدوج). `walletBalance`
ليس قابلاً للإسناد الكتلي في الموديل عمداً.

### 3.2 آلية القفل

- كل من `credit`/`debit` يفتح `DB::transaction`.
- داخل المعاملة يستدعي `lockedBalance()` الذي يقرأ الرصيد بـ **`SELECT … FOR UPDATE`** على صفّ `Customer`.
- يعيد الحساب من قيمة قاعدة البيانات المقفولة (لا من الموديل المُحمَّل قبل المعاملة).
- يُدرِج صفّ `WalletTransaction` بـ `balanceAfter` الجديد ويحدّث `Customer.walletBalance` بنفس القيمة داخل
  نفس المعاملة — فلا ينحرف الرصيد الجاري عن المخزَّن.

### 3.3 credit — الإيداع

المعاملات: `credit(customer, amount, type, note, refId=null, method='CASH', postAccounting=true, collectedAtBranchId=null)`.

خطوة بخطوة:
1. تقريب المبلغ لخانتين؛ رفض ≤ 0 بـ 422 «المبلغ غير صالح».
2. فتح المعاملة، قفل صفّ العميل، حساب `newBalance = current + amount`.
3. إدراج `WalletTransaction` بالنوع المُمرَّر و`balanceAfter = newBalance`.
4. تحديث `Customer.walletBalance`.
5. إذا `postAccounting = true` **و** `type === 'TOPUP'` فقط: نشر قيد الشحن (Dr نقد/بنك / Cr إيراد مؤجَّل)
   عبر `AccountingCore::postWalletTopUp`. **بلا try/catch:** فشل القيد يُرجِع الشحن كاملاً — فلا تحمل
   المحفظة نقداً لا تُظهره الدفاتر.
6. إرجاع `{balance, txnId}`.

**`collectedAtBranchId`:** يختم الدرج (الفرع) الذي حصّل النقد فعلاً؛ إذا غاب يرجع لفرع العميل المنزلي —
وهو تخمين فقط. مطابقة الوردية والدرج تعتمد على هذا: عميل خُدِم في فرع آخر بلا هذا الحقل يُضاف رصيده لدرج خاطئ.

### 3.4 debit — الصرف

المعاملات: `debit(customer, amount, note, refId=null)` — النوع دائماً `DEBIT`.

خطوة بخطوة:
1. تقريب، رفض ≤ 0.
2. قفل صفّ العميل، **فحص كفاية الرصيد على القيمة المقفولة** — رفض `current < amount` بـ 422
   «رصيد المحفظة غير كافٍ». (الفحص على الموديل المُحمَّل مسبقاً يسمح لخصمين متزامنين بتجاوز الحارس معاً → سحب زائد.)
3. حساب `newBalance = current − amount`، إدراج صفّ `DEBIT`، تحديث الرصيد.
4. إرجاع `{balance, txnId}`.

### 3.5 مستدعو المحفظة (نقاط اللمس)

| المستدعي | الحركة | التفاصيل |
|---|---|---|
| `WalletController::topup` | `credit` TOPUP | شحن يدوي؛ `collectedAtBranchId` = فرع الطلب الحالي؛ صلاحية `customers.manage`؛ يُصدر فاتورة شحن ويكتب سجل تدقيق `WALLET_TOPUP`. |
| `PosController::settleWithWallet` | `debit` | دفع سلة من المحفظة؛ قراءة رصيد مقفولة أولاً؛ يتطلب OTP consent مُبرهَن في `store()`. |
| `PosController` (فائض نقدي) | `credit` TOPUP | `overpayTo=WALLET`: الفائض عن المطلوب يصير شحناً (Dr نقد / Cr مؤجَّل) ليطابق النقد المُحصَّل. |
| `OrderDetailController::storePayment` (WALLET) | `debit` | سداد طلب من المحفظة؛ يتطلب OTP consent (§5 أدناه). |
| `OrderDetailController` (إلغاء سلة مدفوعة محفظةً) | `credit` REFUND | `postAccounting=false`؛ يُنشر قيد استعادة الالتزام يدوياً؛ محروس بفحص idempotency (source=ORDER, refType=OrderWalletRefund, refId=order.id). |
| `LoyaltyController` (استبدال نقاط) | `credit` TOPUP | تحويل نقاط الولاء لرصيد محفظة. |

### 3.6 تدفّق الفلوس (المحفظة)

- **الشحن نقداً** ⇒ نقد في الدرج، ورصيد على العميل، وقيد Dr نقد / Cr إيراد مؤجَّل (المبلغ يجلس كالتزام).
- **الدفع من المحفظة** ⇒ لا نقد يتحرّك، لا قيد شحن؛ الاستهلاك يُبَوِّب Dr إيراد مؤجَّل / Cr ذمم مدينة
  (القيمة كانت جالسة بالفعل كالتزام مؤجَّل — انظر ملف 08).
- **الاسترجاع** ⇒ إعادة القيمة للرصيد، واستعادة الالتزام المؤجَّل، لا حركة نقد.

### 3.7 سجل الحركة

`WalletService::history(customerId, limit=50)` يرجع أحدث الحركات أولاً؛ `WalletController::transactions`
يُظهرها مع الرصيد الحالي.

## 4. طرق الدفع (نظرة موحّدة عبر نقاط الدخول الثلاث)

تُسجَّل المدفوعات عبر ثلاث نقاط دخول، كلٌّ بقواعده:

| نقطة الدخول | الطرق المتاحة | البوابة؟ | التسوية؟ | التحقق |
|---|---|---|---|---|
| **POS** (`PosController::store`) | CASH / CARD / TRANSFER / WALLET (+ فائض→WALLET) | لا | لا (درج المنشأة) | WALLET يتطلب OTP consent + TokenDenylist reserve. |
| **تفاصيل الطلب** (`OrderDetailController::storePayment`) | CASH / CARD / TRANSFER / WALLET / DEFERRED | لا | لا | WALLET يتطلب OTP token صالح + `TokenDenylist::reserve`. |
| **صفحة الدفع العامة** (`PayController::pay`) | mada / card / stcpay / applepay (كلها CARD في الدفتر) | نعم | نعم (بركة التسويات، `viaGateway=true`) | التوكن الموقّع هو القدرة الوحيدة؛ المبلغ يُعاد حسابه خادمياً. |

قواعد مشتركة عبر النقاط الثلاث:
1. المبلغ يُقصَّر دائماً على المتبقّي (`grandTotal − paidTotal`) — لا فرط تحصيل.
2. القراءة تحت قفل صفّي على الطلب قبل الكتابة (لا يفقد دفعان متزامنان بعضهما).
3. `paidTotal` يُسقَّف عند `grandTotal`؛ `paymentStatus` = `PAID` إذا سُدِّد كاملاً، وإلا `PARTIAL`.
4. الطلب المُلغى (`CANCELLED`) يُرفض في كل نقطة — أُعيدت إيراداته وتحصيله يترك الذمم برصيد دائن.

## 5. الدفع الأونلاين

### 5.1 اختيار البوابة (Gateway resolution)

`PaymentGateway` يُربَط في `AppServiceProvider` وقت الطلب:
1. `$driver = config('services.payment.driver')` (env `PAYMENT_GATEWAY_DRIVER`).
2. إذا null: `stub` محلياً/اختباراً، وإلا `moyasar`.
3. إذا `driver === 'stub'`: `StubGateway` **فقط** محلياً/اختباراً؛ في الإنتاج `UnavailableGateway`
   («بوابة الدفع التجريبية غير مسموحة في بيئة الإنتاج») — fail-closed.
4. إذا `driver === 'moyasar'` و`services.moyasar.secret` مضبوط: `MoyasarGateway`؛ وإلا `UnavailableGateway`
   («بوابة الدفع الإلكتروني غير مهيأة»).

**البوابات الثلاث:**
- **StubGateway:** بلا نداء شبكي؛ يعامل الشحنة كأنها حُصِّلت فوراً ويرجع مرجعاً وهمياً `poc_…`. محلي فقط.
- **MoyasarGateway:** يتحقق حقيقةً (انظر §5.3).
- **UnavailableGateway:** يُجهض 503 دائماً — الإنتاج بلا اعتماد كامل يفشل مغلقاً بدل تعليم الفواتير مدفوعة زوراً.

### 5.2 رابط الدفع (PayToken + الصفحة العامة)

**`PayToken`** توكن HMAC-SHA256 موقّع بلا حالة، صيغته `{oid, exp}` (base64url) + `~` + توقيع.
مطابق لـ `pay-token.ts` في تطبيق Next.js:
- الفاصل `~` (لا `.`) لأنه غير محجوز في RFC 3986 ولا يظهر في أبجدية base64url — فيسقط نظيفاً في مسار `/pay/{token}`.
- الحمولة معرّف الطلب فقط (لا مطالبات مستأجر).
- المقارنة timing-safe (`hash_equals`)، ومهلة افتراضية 72 ساعة.
- **التوكن هو القدرة الوحيدة**: يخوّل دفع **ذلك الطلب** فقط؛ المبلغ يُعاد حسابه خادمياً دائماً، لا يؤخذ من التوكن.
- `verify` يرجع معرّف الطلب لتوكن صالح غير منتهٍ، و`expired` تميّز التوكن المنتهي (توقيع صالح، `exp` مضى) → HTTP 410.

**إنشاء الرابط** — `POST /orders/{id}/payment-link` (موظف، auth.api):
1. صلاحية `orders.manage`.
2. الطلب مقيّد على فروع المنشأة المُتصِلة (لا يُوثَق بـ orderId خام) — 404 إن لم يوجد.
3. رفض 422 إذا كان الطلب `CANCELLED` (لا يُصَك رابط لسلّة أُعيدت إيراداتها).
4. رفض 422 «الطلب مدفوع بالكامل» إذا `grandTotal − paidTotal ≤ 0`.
5. إصدار `PayToken`، وإرجاع `{token, path: /pay/{token}, url: WEB_URL + path}`.

**صفحة الدفع (تحميل)** — `GET /pay/{token}` (عام، throttle 60/1):
- يحلّ التوكن لطلبه: 404 لتوكن باطل/مُعبَث/طلب محذوف، 410 لمنتهٍ.
- يرجع `orderNo`، اسم البائع (من منشأة الطلب ثم الفرع)، `amountDue` = grandTotal − paidTotal مُعاد حسابه حيّاً
  (0 للطلب المُلغى ليمنع تحميل نموذج البطاقة له)، العملة، علم `paid`، **المفتاح المنشور (publishable) فقط**
  (عام بطبيعته، هو ما يوثّق به نموذج البطاقة المستضاف؛ null ⇒ لا بوابة حيّة والصفحة ترجع لأزرار القنوات — stub محلي)،
  و`orderId` (يختمه النموذج ليمنع إعادة تشغيل الالتقاط ضد طلب آخر).

### 5.3 Moyasar capture — شروط القبول

`MoyasarGateway::capture(order, amount, channel, paymentRef)`:
1. رفض 422 إذا غاب `paymentRef` (معرّف عملية من نموذج مستضاف).
2. إعادة جلب العملية خادمياً بالمفتاح السرّي: `GET {base}/payments/{paymentRef}` (Basic Auth بالسرّ)،
   مهلة 20ث قراءة / 5ث اتصال.
3. رفض 502 إذا فشل النداء.
4. **شروط القبول (كلها معاً، وإلا 402 «لم يتم تأكيد الدفع»):**
   - `status === 'paid'`، **و**
   - `amount` (بالهللات: `round(amount*100)`) يطابق المطلوب تماماً، **و**
   - `currency` (كبير) = `SAR`.
5. **ربط `metadata.order_id`:** إذا حملت الشحنة `metadata.order_id`/`orderId` وجب أن تساوي `order.id`، وإلا
   402 «عملية الدفع لا تخص هذا الطلب». **الربط شرطي (فجوة متبقية):** غياب الـ metadata مقبول للتوافق الرجعي —
   يُرفض فقط المعرّف **المتضارب**، لا المعرّف **الغائب**. (الويبهوك بالعكس يشترط وجود order_id ليسوّي أصلاً.)
6. إرجاع `payment.id` (أو `paymentRef`).

**التنفيذ خارج المعاملة:** `capture()` نداء GET للقراءة فقط (النموذج المستضاف شحن البطاقة فعلاً) ويُنفَّذ
**قبل** فتح معاملة الدفع. السبب: لو نُودِي داخل المعاملة لأمسك قفلاً حصرياً على صفّ الطلب واتصال بوستجرس تحته
طوال ردّ Moyasar (حتى 25ث) — والاتصالات مجمّع ثابت، فبوابة بطيئة تُعطِّل كل كاتب في الطابور وتفشل الكتابة عبر
كل الـ API.

### 5.4 تنفيذ الدفع — `POST /pay/{token}` (عام)

خطوة بخطوة:
1. حلّ التوكن لطلبه (404/410).
2. التحقق من المدخلات: `channel` (اختياري، من `mada/card/stcpay/applepay`)، `amount` (اختياري > 0، ≤ مليون)،
   `paymentRef` (اختياري، مطلوب في الوضع الحيّ فقط). القناة الافتراضية `card`.
3. فحوص مبكّرة (تُعاد تحت القفل حيث تكون موثوقة): رفض الطلب المُلغى؛ إذا `due ≤ 0` يرجع استجابة التسوية.
4. المبلغ = min(المُدخَل، المتبقّي) أو المتبقّي كاملاً.
5. **`capture()` قبل المعاملة** (§5.3)؛ رفض 502 إذا رجع مرجع فارغ.
6. **المعاملة:**
   - إن وُجد `paymentRef`: **قفل استشاري** `pg_advisory_xact_lock(hashtext(paymentRef))` — يسلسل كل طلب يقدّم
     نفس معرّف الدفع المستضاف حتى لو جرّبه مهاجم ضد طلب/قناة مختلفة.
   - قفل صفّ الطلب (`lockForUpdate`).
   - إعادة فحص الإلغاء تحت القفل (السلّة قد تُلغى والعميل على الصفحة، ورابط قديم يبقى صالحاً حتى ينتهي).
   - اشتقاق المتبقّي تحت القفل؛ إذا `≤ 0` لا يُنشر (تسوية سبقته).
   - **مفتاح idempotency القانوني** = `gateway:{txnId}` فقط — يستثني عمداً القناة ومعرّف الطلب (اللذين يتحكم بهما العميل).
   - قفل استشاري ثانٍ على `gateway:{txnId}`.
   - البحث عن دفعة موجودة بنفس المرجع (+ مراجع قديمة `{channel}:{txnId}` للتوافق): إن وُجدت لطلب آخر → 409
     «تم استخدام عملية الدفع لطلب آخر»؛ وإلا لا يُنشر (idempotent).
   - `applied = min(amount, remaining)`.
   - إنشاء `Payment` (method=CARD، **`viaGateway=true`** ⇒ بركة التسويات).
   - إنشاء `OnlineCharge` موازٍ (provider من الإعداد أو stub/moyasar، purpose=ORDER_PAYMENT، status=PAID،
     idempotencyKey=المرجع، rawStatus=paid).
   - رفع `paidTotal` مُسقَّفاً عند `grandTotal`؛ ضبط `paymentStatus`.
   - أرشفة/فتح الطلب (DELIVERED && PAID → مؤرشف).
7. **بعد الالتزام:** نشر التحصيل للدفتر عبر `AccountingCore::syncOrderAccounting` (فشل المزامنة يُسجَّل ولا يكسر الدفع).
8. إرجاع استجابة التسوية (الحالة، paid، paidTotal، amountDue).

### 5.5 الويبهوك — `POST /payments/webhook` (عام)

**لماذا موجود:** بطاقة تمرّ بـ 3-D Secure أو STC Pay/Apple Pay تكتمل عند Moyasar حتى لو أغلق العميل التبويب
قبل إعادة توجيهه — الشحنة تُلتقط والطلب يبقى غير مدفوع للأبد. الويبهوك المسار الوحيد المستقلّ عن بقاء متصفّح العميل.

**fail-closed + HMAC + تسوية مرّة واحدة:**
1. إذا `services.moyasar.webhook_secret` فارغ: **503 fail-closed** (بلا سرّ يستطيع أيٌّ نشر «paid» وتسوية أي طلب مجاناً).
2. مقارنة `secret_token` من **جسم الطلب** (لا ترويسة) بالسرّ المتوقّع عبر `hash_equals`؛ عدم التطابق → 401
   (ليُرى الخطأ في الإعداد). ملاحظة: السرّ يصل في الجسم لأن هكذا تُهيّئه Moyasar.
3. استخراج `type` و`data.id` (txnId)؛ بلا id → 200 متجاهَل.
4. **أحداث الاسترجاع** (`payment_refunded`): تحديث `OnlineCharge` المطابق للـ providerRef إلى `REFUNDED` → 200.
5. **أحداث الدفع** (`payment_paid`/`payment_captured`): إعادة جلب العملية خادمياً بالمفتاح السرّي (لا يوثَق بجسم
   الطلب فوق الـ id)؛ إن لم تكن `paid` → 200 متجاهَل.
6. استخراج `metadata.order_id`؛ **غيابه → 200 متجاهَل** (شحنات الاشتراك/الأجهزة تسوّيها تدفقاتها).
7. `settle()`: نفس مسار كتابة `PayController::pay` وبنفس مفتاح idempotency `gateway:{txnId}`:
   - قفل استشاري على `payref:gateway:{txnId}`.
   - إن وُجدت دفعة بالمرجع → لا شيء (سوّاها ردّ المتصفّح).
   - قفل صفّ الطلب؛ إن غاب → لا شيء.
   - إن كان الطلب `CANCELLED` → لا يسوّي، ويُسجَّل تحذير (البوابة تحمل المال — استرجاع من لوحة Moyasar لا تسوية).
   - إن `remaining ≤ 0` أو `applied ≤ 0` → لا شيء.
   - إنشاء Payment (viaGateway=true) + OnlineCharge (provider=moyasar) + تحديث paidTotal/paymentStatus.
   - بعد الالتزام: `syncOrderAccounting` (فشله يُبلَّغ ولا يُلغي التقاطاً حقيقياً).
8. **يجيب 200 دائماً** لما عالجه أو تجاهله عمداً (Moyasar تعيد المحاولة على غير-2xx — إعادة حدث اخترنا تجاهله تدور للأبد).
   السرّ الخاطئ 401 ليُرى، والإعداد الناقص 503.

**التسوية مرّة واحدة:** أياً وصل ثانياً (ردّ المتصفّح أو الويبهوك أو إعادات محاولة Moyasar) يصبح no-op بفضل
المفتاح المشترك `gateway:{txnId}`.

## 6. التسويات للمنشآت (Payouts)

### 6.1 البركة غير المسوّاة (Unsettled pool)

البركة = صفوف `Payment` حيث `viaGateway = true` **و** `settlementId IS NULL` — أموال حُصِّلت على حساب بوابة
المنصّة نيابةً عن المنشأة (روابط الدفع / بوّابة العميل). النطاق المستأجري يُحلّ عبر `Order → Branch → orgId`
(الطلب لا يحمل orgId مباشرة).

- `unsettledSummary(orgId)` → `{gross, count, from, to}` لمنشأة.
- `balances()` → أرصدة كل المنشآت (لتبويب balances في الأدمن) مرتبة تنازلياً بالإجمالي.

### 6.2 إنشاء الدفعة — `createBatch(orgId, opts)`

يطالِب بركة المنشأة كاملةً في دفعة جديدة ذرّياً:
1. رفض 404 إذا كانت المنشأة منشأة المنصّة نفسها.
2. `Organization::findOrFail`.
3. **قفل استشاري لكل منشأة** `pg_advisory_xact_lock(hashtext('payout:'+orgId))` — يسلسل الإنشاء المتزامن.
4. رفض 409 إذا وُجدت دفعة بحالة مفتوحة (`PENDING_APPROVAL`/`APPROVED`) لهذه المنشأة.
5. لقطة واحدة (ids + amounts معاً) للبركة؛ رفض 422 إذا فرغت.
6. حساب `gross = مجموع المبالغ`؛ الرسوم = المُمرَّرة (مقصورة بين 0 والإجمالي) أو `defaultFee(gross)`.
7. لقطة بنك من `org.payoutConfig.bank`.
8. إنشاء `PayoutSettlement` (status=PENDING_APPROVAL، الفترة، العدّ، gross/fee/net، bankSnapshot، requestedById/createdById/note).
9. **حجز المدفوعات:** `UPDATE Payment SET settlementId=… WHERE id IN (…) AND settlementId IS NULL`؛
   رفض 409 إذا لم يُحجز العدد كاملاً (دفعة متسابقة).
10. **الفهرس الفريد الجزئي** `PayoutSettlement_orgId_open_key` (دفعة مفتوحة واحدة لكل منشأة) يسند القفل: خطأ 23505 → 409.

### 6.3 حساب الرسوم والصافي

`defaultFee(gross) = min(max(0, feeFixed + gross * feePercent/100), gross)` من إعدادات المنصّة.
`netAmount = gross − fee`. القيم الافتراضية: `feeFixed=0`، `feePercent=0`، `minAmount=0`، `requiredApprovals=2`،
`defaultDays=['MON']`.

### 6.4 آلة حالات التسوية (maker-checker)

```
                (createBatch / requestUrgent / runDue)
                              │
                              ▼
                    ┌──────────────────┐
     reject ────────┤ PENDING_APPROVAL ├──── approve×N ───► APPROVED ──── markSent ──► SENT
       │            └──────────────────┘                      │
       │                    │ cancel                          │ cancel
       ▼                    ▼                                 ▼
   REJECTED             CANCELLED                         CANCELLED
   (release)            (release)                         (release)
```

- **PENDING_APPROVAL → APPROVED:** يتطلب N أصوات `APPROVE` مميّزة (`requiredApprovals`). الصوت رقم N يضبط
  `status=APPROVED` و`approvedAt`.
- **PENDING_APPROVAL → REJECTED:** رفض واحد يقتل الدفعة، يسجّل `rejectedReason`، **ويُطلق مدفوعاتها للبركة**.
- **APPROVED → SENT:** `markSent` بـ transferRef؛ يسجّل sentAt/sentById/transferRef ويُشعِر المنشأة.
- **cancel (من أي حالة مفتوحة):** `CANCELLED` + إطلاق المدفوعات. لا يُلغى ما هو `SENT` أو مغلق.
- **إطلاق المدفوعات** (`releasePayments`): `UPDATE Payment SET settlementId=NULL WHERE settlementId=…` — تعود للبركة.

**قواعد maker-checker:**
1. **N أصوات مميّزة** (`payouts.requiredApprovals`، 1–5، افتراضي 2).
2. **المُنشئ لا يصوّت:** إذا `createdById === adminId` عند approve → 403 «مُنشئ التسوية لا يمكنه الموافقة».
3. **صوت واحد لكل أدمن:** التصويت المزدوج يصطدم بالفهرس الفريد → 409 «سبق أن صوّتّ».
4. **تعديل الرسوم يمسح الأصوات:** `updateFee` (متاح PENDING_APPROVAL فقط) يعيد حساب fee/net **ويحذف كل أصوات
   الموافقة** — لأن المبالغ التي رآها المصوّتون تغيّرت.
5. **markSent يُظهر IBAN كاملاً فقط لحامل `manage_payouts`** (مُنفِّذ التحويل)؛ غيره ممّن يملك `view_finance`
   يرى IBAN مُقنَّعاً (`****` + آخر 4).

### 6.5 تدفّق الفلوس (التسوية)

المنصّة تحتجز مدفوعات البوابة (`viaGateway`) ⇒ تُجمَّع في دفعة ⇒ بعد N موافقات تُحوَّل بنكياً للمنشأة بعد خصم
رسوم المنصّة. الإشعار للمنشأة يوضّح: الصافي = الإجمالي − الرسوم + رقم الحوالة.

### 6.6 الجدولة الأسبوعية والطلب العاجل

- **الجدولة (جهة المنشأة):** المالك (SUPER_ADMIN) يضبط `payoutConfig.days` (يوم أو يومان بالأسبوع كحد أقصى)
  والحساب البنكي المستقبِل (iban بصيغة `SA` + 22 رقماً، bankName، beneficiary).
- **الطلب العاجل:** المالك يطلب تسوية فورية للرصيد الحالي — يتطلب iban مضبوطاً أولاً (422 إن غاب)؛ ينشئ دفعة
  `urgent=true` بـ `requestedById`.
- **السحب المجدوَل (المنصّة):** `runDue(today)` يمرّ على أرصدة كل المنشآت: يتخطّى ما دون `minAmount`، ويتخطّى
  المنشأة التي لا يشمل جدولها اليوم (`payoutConfig.days` أو `defaultDays`)، وإلا ينشئ دفعة؛ استثناءات 409/422
  تُتخطّى ولا توقف السحب. يرجع `{created:[...orgIds], skipped:int}`.

## 7. سجلات المنصّة

### 7.1 سجل المدفوعات — `GET /platform/payments`

عرض مالك المنصّة لكل `OnlineCharge` عبر كل المنشآت (مقرون باسم المنشأة). مقيّد بـ `assertPlatformOwnerRole`
(403 لغير المالك). مرشّحات اختيارية: `status` (من enum)، `orgId`، `from`/`to` (حدود يوم شاملة). أحدث أولاً،
حد 500 صف. ملخّص فوق نفس المجموعة المُرشَّحة: `totalPaid`, `totalRefunded`, `failedCount`, `count`.

### 7.2 سجل مبيعات المنصّة — `GET /platform/sales` + `/export.csv`

دفتر مبيعات/اشتراكات المنصّة (spec 2.2). كل سطر بيع من مصدرين:
- **`SUBSCRIPTION`**: كل `PlatformSubscription` (سطر الاشتراك المتكرّر، بسعر دورته، مؤرَّخ بـ `currentPeriodEnd`).
- **`CHARGE`**: كل `OnlineCharge` بغرض `SUBSCRIPTION` (دفعة فعلية، مؤرَّخة بـ `createdAt`).

كل سطر يحمل المبلغ شامل الضريبة + مكوّن الـ 15% المستخرَج: `vat = round(amount*15/115, 2)` والصافي.
مرشّحات: `from`/`to` (بتاريخ السطر)، `status`، `orgId`. أحدث أولاً. الملخّص: `{gross, vat, net, count}`.
JSON والـ CSV يتشاركان نفس باني الصفوف (CSV مطابق للجدول حرفاً بحرف، مع BOM لعرض العربي في Excel).
مقيّد بـ `assertPlatformOwnerRole`.

## 8. قواعد البيزنس (مرقّمة)

1. كل حركة محفظة تمرّ عبر `WalletService` حصراً (قفل `FOR UPDATE`؛ لا كتابة رصيد يدوية).
2. الشحن (TOPUP) ينشر Dr نقد/بنك / Cr إيراد مؤجَّل؛ الدفع/الاشتراك المدفوع محفظةً لا ينشر قيداً (القيمة في
   الالتزام المؤجَّل)؛ الاستهلاك ينشر Dr مؤجَّل / Cr ذمم.
3. فحص كفاية رصيد الخصم على القيمة المقفولة فقط (لا الموديل المُحمَّل مسبقاً).
4. `balanceAfter` يُكتب داخل نفس معاملة تحديث الرصيد فلا ينحرف.
5. `collectedAtBranchId` يختم الدرج المُحصِّل الحقيقي (مطابقة الوردية تعتمد عليه).
6. خصم المحفظة الحاضر-العميل (POS/تفاصيل الطلب WALLET) يتطلب OTP consent + `TokenDenylist::reserve` (حرق الـ jti
   ذرّياً قبل تحرّك المال — انظر ملف 00 §نقاط البيع).
7. المبلغ يُعاد حسابه خادمياً دائماً من الطلب؛ لا يؤخذ من التوكن أو العميل؛ ويُقصَّر على المتبقّي (لا فرط تحصيل).
8. `PayToken` هو القدرة الوحيدة في الرابط: يخوّل دفع طلب واحد؛ توقيع timing-safe؛ منتهٍ → 410، باطل → 404.
9. اختيار البوابة fail-closed: الإنتاج بلا اعتماد كامل → `UnavailableGateway` (503)؛ stub محلي/اختبار فقط.
10. Moyasar يقبل الالتقاط فقط عند `status=paid` **و** تطابق المبلغ بالهللات **و** العملة SAR.
11. ربط `metadata.order_id` **شرطي** في capture: يُرفض المعرّف المتضارب لا الغائب (فجوة متبقية)؛ الويبهوك بالعكس
    يشترط وجوده ليسوّي.
12. `capture()` يُنفَّذ خارج معاملة الدفع (نداء GID للقراءة؛ يمنع حجز اتصال بوستجرس تحت قفل الطلب طوال ردّ البوابة).
13. مفتاح idempotency القانوني = `gateway:{txnId}` فقط (يستثني القناة ومعرّف الطلب المتحكَّم بهما عميلياً)؛
    مُدعَّم بقفل استشاري.
14. دفعة رابط الدفع تُنشئ `Payment(viaGateway=true)` **و** `OnlineCharge` موازياً (وإلا لم تظهر في مراقب المنصّة).
15. الويبهوك fail-closed: بلا سرّ → 503؛ سرّ خاطئ → 401؛ يعيد الجلب الموثوق ويسوّي مرّة واحدة بالمفتاح المشترك.
16. الطلب المُلغى (CANCELLED) يُرفض دفعه في كل مسار (رابط، ويبهوك، تفاصيل الطلب) — تحصيله يترك الذمم برصيد دائن؛
    الويبهوك يسجّل تحذيراً (استرجاع من لوحة Moyasar).
17. البركة غير المسوّاة = `Payment.viaGateway=true AND settlementId IS NULL` (النطاق عبر Branch→org).
18. إنشاء الدفعة ذرّي: قفل استشاري لكل منشأة + فهرس فريد جزئي (دفعة مفتوحة واحدة لكل منشأة) + حجز مشروط بـ
    `settlementId IS NULL`.
19. maker-checker: N أصوات مميّزة؛ المُنشئ لا يصوّت؛ صوت واحد لكل أدمن؛ رفض واحد يقتل ويُطلق؛ تعديل الرسوم يمسح الأصوات.
20. الرفض/الإلغاء يُطلق مدفوعات الدفعة للبركة (`settlementId=NULL`)؛ لا يُلغى ما هو SENT.
21. IBAN كامل فقط لحامل `manage_payouts`؛ حامل `view_finance` فقط يراه مُقنَّعاً.
22. `markSent` يشعِر المنشأة (إعلان منصّة + واتساب اختياري)؛ فشل الإشعار لا يُخفي تحويلاً مسجَّلاً (المال أولاً، الآثار الجانبية best-effort).
23. الجدولة يوم أو يومان بالأسبوع كحد أقصى؛ الطلب العاجل يتطلب iban مضبوطاً؛ السحب المجدوَل يتخطّى ما دون `minAmount` أو خارج الجدول.
24. الدفعة الآجلة (DEFERRED) علامة حالة لا تحصيل: لا Payment ولا قيد.
25. الفائض النقدي عند `overpayTo=WALLET` يصير شحناً (Dr نقد / Cr مؤجَّل) ليطابق النقد المُحصَّل؛ الفائض CHANGE يُعاد نقداً بلا قيد.

## 9. الأدوار والصلاحيات لكل عملية

| العملية | نقطة النهاية | الحارس |
|---|---|---|
| شحن المحفظة | `POST /customers/{id}/wallet/topup` | صلاحية `customers.manage` + تقييد المنشأة. |
| حركة المحفظة | `GET /customers/{id}/wallet/transactions` | تقييد المنشأة (ownedCustomer). |
| إنشاء رابط دفع | `POST /orders/{id}/payment-link` | صلاحية `orders.manage` + تقييد فروع المنشأة. |
| تحميل صفحة الدفع | `GET /pay/{token}` | **عام** — التوكن الموقّع هو القدرة الوحيدة. |
| تنفيذ الدفع | `POST /pay/{token}` | **عام** — التوكن + إعادة حساب المبلغ خادمياً. |
| الويبهوك | `POST /payments/webhook` | **عام** — سرّ مشترك (HMAC) في الجسم، بلا bearer. |
| تسوية (منشأة): عرض | `GET /payouts` | `requireManager`. |
| تسوية (منشأة): جدولة/بنك | `PATCH /payouts/config` | `requireSuperAdmin` (يحرّك مال المنشأة). |
| تسوية (منشأة): طلب عاجل | `POST /payouts/request` | `requireSuperAdmin` + iban مضبوط. |
| تسوية (أدمن): قراءة/CSV/settings-عرض | `GET /admin/payouts*`, `.../settings` | `view_finance` **أو** `manage_payouts`. |
| تسوية (أدمن): إنشاء/سحب/موافقة/رفض/رسوم/تحويل/إلغاء/settings-تعديل | `POST/PATCH .../admin/payouts*` | `manage_payouts` (جلسة أدمن منصّة حيّة). |
| سجل مدفوعات المنصّة | `GET /platform/payments` | `assertPlatformOwnerRole` (المالك فقط). |
| مبيعات المنصّة + CSV | `GET /platform/sales`, `/export.csv` | `assertPlatformOwnerRole`. |

> صلاحيات `/admin/*` تُعاد التحقق منها من قاعدة البيانات الحيّة كل طلب (جلسة `kind:platform`)، فتعطيل/تنزيل أدمن
> يسري فوراً؛ المالك (OWNER) يتجاوز كل الصلاحيات. `/platform/*` تُقيَّد بـ `assertPlatformOwnerRole` (لا خريطة صلاحيات granular).

## 10. قائمة العمليات الكاملة

**المحفظة:**
1. `POST /customers/{id}/wallet/topup` — شحن + فاتورة شحن + سجل تدقيق.
2. `GET /customers/{id}/wallet/transactions` — الرصيد + سجل الحركة.

**رابط الدفع + صفحة الدفع (عامة):**
3. `POST /orders/{id}/payment-link` — صكّ رابط لطلب غير مدفوع.
4. `GET /pay/{token}` — ملخّص الطلب للصفحة العامة.
5. `POST /pay/{token}` — تنفيذ الدفع عبر البوابة.
6. `POST /payments/webhook` — ويبهوك Moyasar (تسوية/استرجاع).

**التسويات (جهة المنشأة):**
7. `GET /payouts` — الرصيد + الإعداد + التاريخ.
8. `PATCH /payouts/config` — الجدولة + الحساب البنكي.
9. `POST /payouts/request` — طلب تسوية عاجلة.

**التسويات (أدمن المنصّة):**
10. `GET /admin/payouts` — قائمة الدفعات (مرشّحات + عدّ الأصوات).
11. `POST /admin/payouts` — إنشاء دفعة لمنشأة.
12. `GET /admin/payouts/balances` — أرصدة كل المنشآت غير المسوّاة.
13. `POST /admin/payouts/run-due` — تشغيل السحب المجدوَل الآن.
14. `GET /admin/payouts/export.csv` — CSV الدفعات.
15. `GET /admin/payouts/settings` — عرض إعدادات التسوية.
16. `PATCH /admin/payouts/settings` — تعديل الإعدادات (أصوات/رسوم/حد/أيام).
17. `GET /admin/payouts/{id}` — تفاصيل دفعة (مدفوعات + أصوات).
18. `GET /admin/payouts/{id}/payments.csv` — CSV مدفوعات الدفعة.
19. `POST /admin/payouts/{id}/approve` — تصويت موافقة.
20. `POST /admin/payouts/{id}/reject` — تصويت رفض (يقتل + يُطلق).
21. `PATCH /admin/payouts/{id}/fee` — تعديل الرسوم (يمسح الأصوات).
22. `POST /admin/payouts/{id}/sent` — تسجيل التحويل + إشعار.
23. `POST /admin/payouts/{id}/cancel` — إلغاء دفعة مفتوحة (يُطلق).

**سجلات المنصّة:**
24. `GET /platform/payments` — سجل المدفوعات عبر المنشآت.
25. `GET /platform/sales` — دفتر مبيعات المنصّة.
26. `GET /platform/sales/export.csv` — CSV المبيعات.

## 11. حالات خاصة وفجوات معروفة

1. **ربط metadata.order_id شرطي في capture:** `MoyasarGateway::capture` يرفض المعرّف **المتضارب** فقط،
   ويقبل الشحنة بلا metadata للتوافق الرجعي. أي شحنة Moyasar `paid` بالمبلغ والعملة الصحيحين بلا order_id تُقبَل
   لأي طلب يقدّم مرجعها. التخفيف الحالي: النموذج المستضاف يُفترض أن يختم order_id، والويبهوك (المسار الأكثر موثوقية)
   **يشترط** وجوده. (فجوة متبقية موثّقة في تعليق الكود.)
2. **الطلب المُلغى المدفوع عبر الويبهوك:** البوابة تحمل المال لكن التسوية تُرفض؛ يُسجَّل تحذير — يتطلب **استرجاعاً
   يدوياً من لوحة Moyasar**، لا معالجة آلية.
3. **مراجع القنوات القديمة:** `pay()` يفحص مراجع `{channel}:{txnId}` القديمة إلى جانب `gateway:{txnId}` للتوافق
   الرجعي مع مدفوعات سُجِّلت قبل توحيد المفتاح.
4. **StubGateway في الإنتاج:** ممنوع صراحةً (`UnavailableGateway`)؛ لكن ضبط `PAYMENT_GATEWAY_DRIVER=stub`
   خطأً في الإنتاج يفشل الدفع (503) بدل تسويته زوراً — سلوك مقصود.
5. **فرع التحصيل المُخمَّن:** `collectedAtBranchId` إن غاب يرجع لفرع العميل المنزلي — تخمين قد يخطئ درج الوردية.
6. **الأصوات الممسوحة بعد تعديل الرسوم:** تعديل الرسوم على دفعة كانت شبه مكتملة الموافقة يعيدها لصفر أصوات؛
   قد يتطلب جولة موافقة كاملة جديدة.
7. **قصر الحدود:** سجل المدفوعات محدود بـ 500 صف، سجل التسويات 300 (CSV 5000)، مبيعات المنصّة بلا صفحنة
   (تُبنى في الذاكرة وتُفرَز بـ usort) — قد يثقل مع نموّ البيانات (لا صفحنة/pagination — انظر ملاحظات الأداء في ملف 00).
8. **الاسترجاع عبر الويبهوك يحدّث OnlineCharge فقط:** حدث `payment_refunded` يعلّم `OnlineCharge=REFUNDED` لكنه
   لا يعكس `Payment` ولا الدفتر ولا `paidTotal` — التسوية المحاسبية للاسترجاع خارج مسار الويبهوك.
9. **بركة التسوية لا تعتمد على وقت الطلب:** الفترة (periodStart/End) تُشتقّ من `createdAt` للمدفوعات المحجوزة
   لحظة الإنشاء، فدفعة عاجلة قد تغطّي فترة أوسع/أضيق من الأسبوع المجدوَل.
10. **دفعة مفتوحة واحدة لكل منشأة:** لا يمكن إنشاء دفعة ثانية بينما الأولى `PENDING_APPROVAL`/`APPROVED` —
    يجب إتمامها (SENT) أو إلغاؤها/رفضها أولاً؛ يقيّد تدفّق التسويات المتوازية للمنشأة الواحدة.
