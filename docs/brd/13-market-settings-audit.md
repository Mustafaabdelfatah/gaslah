# BRD 13 — السوق والإعدادات والتدقيق

> يفترض هذا المستند أن القارئ اطّلع على `00-overview-architecture.md` (بنية التوكن HMAC، سمة `ResolvesTenant`، نموذج `PrismaModel`، جدول `Setting` كمخزن key/value، القاعدة المشتركة المُدارة عبر Prisma، وقاعدة الإضافة فقط في المخطط).

---

## 1. نظرة عامة

يغطّي هذا المجال أربعة أنظمة متقاطعة داخل منصة «غسلة»:

1. **السوق B2B (السوق / سوق المستلزمات):** سوق ثنائي الجانب لمستلزمات المغاسل. الجانب المشتري = مستأجرو المنصة (المغاسل) يتصفحون منتجات موردين معتمدين ويضعون طلبات شراء. الجانب المورّد = بوابة مستقلة للموردين لهم تسجيل دخول خاص (بريد + كلمة مرور) يديرون فيها منتجاتهم ويتابعون طلباتهم عبر آلة حالات. المنصة تقتطع **عمولة** من كل طلب وتحسب **صافي مستحقات المورّد** (`supplierPayout`).
2. **الإعدادات (Settings):** ملف المنشأة التجاري (الاسم/العملة/الضريبة)، إعدادات الإيصال، هوية العلامة (ألوان)، وهوية بوابة العميل (شعار/slug/دومين مخصص + محتوى البوابة).
3. **التكوين (Config groups):** مجموعات JSON لكل منشأة: `automation` (أتمتة أزمنة التسليم)، `credit` (حدود الآجل)، `offers` (عرض العروض ومستندات البوابة)، `notifications` (تنبيهات لوحة التحكم).
4. **التكاملات والأسرار (Integrations & secrets):** طرق الدفع المفعّلة، بوابة الدفع الإلكتروني، واتساب، SMS — تُخزَّن أسرارها **مشفّرة** ولا تُرسل للمتصفح أبداً.
5. **سجل التدقيق (AuditLog):** سجل غير قابل للتعديل لِـ«من غيّر ماذا ومتى» مع لقطات before/after، متاح لمدير المنشأة العام فقط.

كل هذه الأنظمة مبنية على تعدد المستأجرين: كل قراءة/كتابة مقيَّدة بـ `orgId` المستخرج من التوكن، لا يُقبل أبداً معرّف منشأة من العميل.

**ملاحظة معمارية مهمة:** جانب المشتري في السوق والإعدادات والتكوين والتكاملات جميعها تحت الوسيط `auth.api` (توكن طاقم). أما بوابة المورّد فتحت `auth.api` أيضاً لكن مع توكن من نوع خاص `kind=supplier` تفرضه سمة `ResolvesSupplier`.

## 2. السوق B2B (السوق)

### 2.1 الكيانات

#### 2.1.1 `MarketSupplier` (المورّد) — جدول `MarketSupplier`

مورّد أعمال في سوق المستلزمات. معتمد من المنصة، يعرض منتجات يتصفحها المستأجرون. له `createdAt` بلا `updatedAt`.

| الحقل | النوع | الوصف |
|------|------|------|
| `id` | نص (cuid) | المفتاح الأساسي |
| `name` | نص | اسم المورّد التجاري |
| `email` | نص | البريد — مفتاح تسجيل الدخول (يُخزَّن/يُطابَق بأحرف صغيرة) |
| `phone` | نص | الهاتف |
| `passwordHash` | نص | هاش bcrypt (`$2b$…`) — **مخفي دائماً** عبر `$hidden`؛ لا يُسلسَل في أي رد |
| `status` | enum نصي | حالة المورّد (انظر 2.1.6) |
| `description` | نص | وصف المورّد |
| `city` | نص | المدينة |
| `logoUrl` | نص | شعار المورّد |
| `commissionType` | enum نصي | نوع العمولة (انظر 2.1.7) — `PERCENT` افتراضياً عند الغياب |
| `commissionValue` | عدد عشري | قيمة العمولة (نسبة % أو مبلغ ثابت بحسب النوع) |
| `createdAt` | تاريخ | تاريخ الإنشاء |
| `approvedAt` | تاريخ | تاريخ الاعتماد (يُقرأ في الكاست) |

العلاقات: `products` (hasMany `MarketProduct`)، `orders` (hasMany `MarketOrder`).

#### 2.1.2 `MarketProduct` (منتج المورّد) — جدول `MarketProduct`

منتج مدرَج من مورّد (مستلزمات/مواد مغاسل). له `createdAt` بلا `updatedAt`.

| الحقل | النوع | الوصف |
|------|------|------|
| `id` | نص (cuid) | المفتاح الأساسي |
| `supplierId` | نص | مالك المنتج (المورّد) |
| `name` | نص | اسم المنتج (عربي) |
| `nameEn` | نص | الاسم الإنجليزي (اختياري) |
| `category` | نص | فئة المنتج (انظر الفئات الثابتة 2.4) |
| `description` | نص | الوصف |
| `unit` | نص | وحدة القياس (افتراضي `قطعة`) |
| `price` | عدد عشري | سعر الوحدة |
| `stock` | عدد صحيح | المخزون (فارغ = غير محدود) |
| `imageUrl` | نص | رابط صورة (http(s):// أو مسار جذري `/`) |
| `isActive` | منطقي | نشط/غير نشط — التفعيل/الإيقاف يمرّ عبر التحديث |
| `createdAt` | تاريخ | تاريخ الإنشاء |

العلاقات: `supplier` (belongsTo)، `items` (hasMany `MarketOrderItem` عبر `productId`).

#### 2.1.3 `MarketOrder` (طلب السوق) — جدول `MarketOrder`

طلب شراء لمستأجر مغسلة من مورّد في السوق. له `createdAt` بلا `updatedAt`.

| الحقل | النوع | الوصف |
|------|------|------|
| `id` | نص (cuid) | المفتاح الأساسي |
| `orgId` | نص | المنشأة المشترية (المستأجر) |
| `branchId` | نص | فرع الطلب (فرع الكاتب) |
| `supplierId` | نص | المورّد — **مورّد واحد لكل طلب** |
| `status` | enum نصي | حالة التنفيذ (انظر 2.1.8) — تبدأ `PENDING` |
| `paymentMethod` | enum نصي | طريقة الدفع `ONLINE`/`DEFERRED` |
| `paymentStatus` | enum نصي | حالة الدفع — تبدأ `UNPAID` |
| `subtotal` | عدد عشري | مجموع الأسطر قبل أي اقتطاع |
| `commissionType` | enum نصي | نوع العمولة المطبَّق (لقطة من المورّد) |
| `commissionRate` | عدد عشري | نسبة العمولة (٪) — 0 لغير PERCENT |
| `commissionAmount` | عدد عشري | مبلغ العمولة المقتطع للمنصة |
| `total` | عدد عشري | الإجمالي الذي يدفعه المشتري = `subtotal` |
| `supplierPayout` | عدد عشري | صافي مستحقات المورّد = `subtotal − commissionAmount` |
| `address` | نص | عنوان (اختياري، في fillable) |
| `notes` | نص | ملاحظات الطلب (حتى 500 حرف) |
| `createdById` | نص | معرّف المستخدم الكاتب (من claims) |
| `createdAt` | تاريخ | تاريخ الإنشاء |
| `deliveredAt` | تاريخ | يُختَم عند الانتقال إلى `DELIVERED` |
| `inventoryApplied` | منطقي | علَم كاست (تطبيق المخزون) — غير مكتوب في المسار الحالي |
| `accountingPosted` | منطقي | علَم كاست (ترحيل محاسبي) — غير مكتوب في المسار الحالي |

العلاقات: `supplier` (belongsTo)، `items` (hasMany `MarketOrderItem` عبر `orderId`).

> ملاحظة: `total = subtotal` دائماً؛ المشتري يدفع القيمة كاملة، والعمولة تُخصم من جهة المورّد فقط (لا تُضاف على المشتري).

#### 2.1.4 `MarketOrderItem` (سطر الطلب) — جدول `MarketOrderItem`

سطر واحد على طلب، بلقطة snapshot للاسم/الوحدة/السعر. **بلا** `createdAt`/`updatedAt`.

| الحقل | النوع | الوصف |
|------|------|------|
| `id` | نص (cuid) | المفتاح الأساسي |
| `orderId` | نص | الطلب المالك |
| `productId` | نص | المنتج المرجعي |
| `name` | نص | لقطة اسم المنتج وقت الطلب |
| `unit` | نص | لقطة الوحدة |
| `unitPrice` | عدد عشري | لقطة سعر الوحدة |
| `quantity` | عدد عشري | الكمية |
| `lineTotal` | عدد عشري | إجمالي السطر = `unitPrice × quantity` (مقرَّب رقمين) |

#### 2.1.5 `Setting` (يُستخدَم غير مباشر) — انظر القسم 3 و7.

#### 2.1.6 حالات المورّد (`MarketSupplier.status`)

| القيمة | المعنى | أثرها |
|------|------|------|
| `PENDING` | قيد المراجعة | يمكنه تسجيل الدخول (يرى شارة حالة)، لكن منتجاته لا تظهر للمشترين |
| `APPROVED` | معتمد | منتجاته النشطة تظهر في السوق ويمكن الطلب منه |
| `REJECTED` | مرفوض | **يُمنع تسجيل الدخول** (403) |
| `SUSPENDED` | موقوف | يمكنه تسجيل الدخول (يرى شارة حالة)، لكن منتجاته لا تظهر للمشترين |

> قاعدة الظهور للمشتري تعتمد حصراً على `status === 'APPROVED'`؛ أي حالة أخرى تخفي منتجات المورّد من تصفّح السوق.

#### 2.1.7 نوع العمولة (`commissionType`)

| القيمة | الحساب | ملاحظة |
|------|------|------|
| `PERCENT` | `commissionAmount = subtotal × value / 100` | `value` نسبة مئوية؛ القيمة الافتراضية للمنصة **8%** عند غياب قيمة المورّد |
| `FIXED` | `commissionAmount = min(max(value, 0), subtotal)` | مبلغ ثابت لكل طلب، **مسقوف بالإجمالي** فلا يتجاوز subtotal |
| `SUBSCRIPTION` | `commissionAmount = 0` | لا اقتطاع لكل طلب (المورّد يدفع اشتراكاً بدلاً من عمولة) |

#### 2.1.8 حالات طلب السوق (`MarketOrder.status`) وآلة الحالات

| القيمة | المعنى |
|------|------|
| `PENDING` | جديد، بانتظار تأكيد المورّد |
| `CONFIRMED` | أكّده المورّد |
| `SHIPPED` | تم الشحن |
| `DELIVERED` | تم التسليم (يُختَم `deliveredAt`) |
| `CANCELLED` | مُلغى |

**آلة الحالات (`SUPPLIER_FLOW`) — الانتقالات المسموحة فقط:**

```
PENDING   → CONFIRMED | CANCELLED
CONFIRMED → SHIPPED   | CANCELLED
SHIPPED   → DELIVERED
DELIVERED → (نهائي)
CANCELLED → (نهائي)
```

أي انتقال خارج هذا الرسم يُرفَض (422 «انتقال غير صالح للحالة»).

#### 2.1.9 طرق الدفع لطلب السوق (`paymentMethod`)

| القيمة | المعنى |
|------|------|
| `ONLINE` | دفع إلكتروني |
| `DEFERRED` | آجل (الافتراضي عند الغياب) |

حالة الدفع (`paymentStatus`) تبدأ دائماً `UNPAID` عند الإنشاء.

### 2.2 جانب المشتري (المستأجر / المغسلة)

كل نقاط المشتري تتطلب ميزة الخطة `supplier_market` عبر `requireFeature($request, 'supplier_market')`، وكلها تحت `assertStaff` ضمناً (لأن `orgId()` تستدعي `assertStaff`).

#### 2.2.1 تصفّح المنتجات — `GET /market/products`

1. تحقّق من ميزة `supplier_market`.
2. اقرأ فلاتر: `category` (اختياري)، `q` (بحث بالاسم، اختياري).
3. استعلم عن `MarketProduct` بشرط:
   - `isActive = true`،
   - **وينتمي لمورّد `status = APPROVED`** (`whereHas('supplier')`)،
   - وإن وُجِد `category` طابِقه،
   - وإن وُجِد `q` طبّق `ILIKE %q%` على الاسم.
4. حمّل بيانات المورّد المختصرة (`id, name, city`)، رتّب تنازلياً بـ `createdAt`، **حدّ أقصى 200 صف**.
5. أعِد `data` + `meta.total` + قائمة `categories` الثابتة.

#### 2.2.2 تفاصيل منتج — `GET /market/products/{id}`

1. تحقّق من الميزة.
2. اجلب المنتج بشرط `id` مطابق **و** `isActive = true` **و** مورّده `APPROVED`.
3. غير موجود → 404 «المنتج غير موجود».
4. أعِد المنتج المُقدَّم (presentProduct).

#### 2.2.3 إنشاء طلب — `POST /market/orders`

آلية «سلة = مورّد واحد». الخطوات:

1. تحقّق من الميزة `supplier_market`.
2. تحقّق من المدخلات: `items[]` (1..500 سطر)، لكل سطر `productId` و`quantity` (>0، حتى 100000)؛ `paymentMethod` (اختياري: `ONLINE`/`DEFERRED`)؛ `notes` (حتى 500).
3. الافتراضي `paymentMethod = DEFERRED` عند الغياب.
4. **دمج المكرّرات:** اجمع كميات نفس `productId` في خريطة واحدة.
5. اجلب المنتجات المطلوبة بشرط `isActive = true` **و** مورّدها `APPROVED`.
6. **قاعدة التوافر:** إن كان عدد المنتجات المُعادة ≠ عدد المعرّفات الفريدة → 422 «أحد المنتجات غير متاح».
7. **قاعدة المورّد الواحد:** إن كان عدد الموردين المميّزين ≠ 1 → 422 «الطلب الواحد يجب أن يكون من مورّد واحد».
8. ابنِ أسطر الطلب بلقطات (name/unit/unitPrice) واحسب `lineTotal = round2(price × qty)`.
9. `subtotal = round2(Σ lineTotal)`.
10. **حساب العمولة:**
    - اجلب المورّد؛ `commissionType = supplier.commissionType ?? 'PERCENT'`.
    - `commissionValue = supplier.commissionValue ?? (PERCENT ? 8 : 0)`.
    - `commissionAmount = computeCommission(type, value, subtotal)` (انظر 2.1.7).
    - `commissionRate = (PERCENT ? value : 0)`.
11. داخل **معاملة DB واحدة**: أنشئ `MarketOrder` بـ:
    - `orgId = orgId()`، `branchId = branchId()`، `supplierId`، `status = PENDING`، `paymentMethod`، `paymentStatus = UNPAID`،
    - `subtotal`، `commissionType`، `commissionRate`، `commissionAmount`، `total = subtotal`، `supplierPayout = round2(subtotal − commissionAmount)`، `notes`، `createdById = claims.userId`.
    - ثم أنشئ الأسطر عبر `items()->createMany`.
12. أعِد الطلب المُقدَّم مع الأسطر والمورّد، **201**.

#### 2.2.4 قائمة طلبات المنشأة — `GET /market/orders`

1. تحقّق من الميزة.
2. اجلب طلبات `orgId = orgId()`، مع `items` و`supplier(id,name,phone)`، تنازلياً بـ `createdAt`، **حد أقصى 100**.
3. أعِد `data` + `meta.total`.

#### 2.2.5 تفاصيل طلب — `GET /market/orders/{id}`

1. تحقّق من الميزة.
2. اجلب طلباً بشرط `id` **و** `orgId = orgId()` (عزل المستأجر).
3. غير موجود → 404 «الطلب غير موجود».
4. أعِد الطلب المُقدَّم.

> جانب المشتري **للقراءة والإنشاء فقط**؛ لا يوجد أي مسار للمشتري لتغيير حالة الطلب أو إلغائه — التحكم في دورة الحياة حصري للمورّد.

### 2.3 جانب المورّد (بوابة المورّد)

بوابة مستقلة، توكن `kind=supplier`. تسجيل الدخول عام؛ بقية النقاط تحت `auth.api` + `ResolvesSupplier` (ترفض أي توكن غير مورّد بـ 401). كل استعلام مقيّد بـ `supplierId` المستخرج من التوكن.

#### 2.3.1 تسجيل الدخول — `POST /supplier/auth/login` (عام، مع throttle:auth-login)

1. تحقّق من `email` و`password`.
2. طبّع البريد (lowercase + trim)، اجلب `MarketSupplier` بالبريد.
3. **رسالة موحّدة:** إن لم يوجد المورّد **أو** فشل `password_verify` → 401 «بيانات الدخول غير صحيحة» (لا تمييز بين بريد مجهول وكلمة مرور خاطئة).
4. إن كانت الحالة `REJECTED` → 403 «تم رفض هذا الحساب».
5. (حالات `PENDING`/`SUSPENDED` تدخل بنجاح — البوابة تعرض شارة حالة).
6. أصدِر توكن `ApiToken` بـ `{supplierId, kind:'supplier'}` لمدة **30 يوماً**.
7. أعِد `token` + `supplier` المُقدَّم (بلا passwordHash).

> **كلمات المرور:** يُستخدم `password_verify()` وليس `Hash::check` (هاشات `$2b$` من bcryptjs تُسقِط `Hash::check` تحت فحص الخوارزمية الصارم في PHP 8.5).

#### 2.3.2 الملف والملخص — `GET /supplier/me`

1. اجلب المورّد بـ `supplierId()`؛ غير موجود → 404.
2. احسب إحصائيات: عدد المنتجات، المنتجات النشطة، عدد الطلبات، الطلبات الجديدة (`status=PENDING`)، ومجموع `supplierPayout` للطلبات `DELIVERED` فقط (payout).
3. أعِد الملف + `stats`.

#### 2.3.3 منتجات المورّد — `GET /supplier/products`

اجلب منتجات `supplierId()` (النشطة وغير النشطة معاً)، تنازلياً بـ `createdAt`. أعِد `data` + `meta.total` + `categories`.

#### 2.3.4 إنشاء منتج — `POST /supplier/products`

1. تحقّق من المدخلات (اسم، فئة، سعر ≥ 0، صورة اختيارية بنمط `^(https?://|/)`، إلخ).
2. أنشئ `MarketProduct` مملوكاً لـ `supplierId()` مع الافتراضيات (`unit='قطعة'`، `isActive=true`).
3. أعِد المنتج المُقدَّم، **201**.

#### 2.3.5 تحديث منتج — `PUT /supplier/products/{id}`

1. اجلب منتجاً بشرط `id` **و** `supplierId = supplierId()`؛ غير موجود → 404 (عزل الملكية).
2. تحقّق من المدخلات.
3. حدّث الحقول؛ `imageUrl` و`isActive` تُحدَّثان فقط إن وُرِدا في الحمولة.
4. **التفعيل/الإيقاف يمر عبر هذه النقطة** (تبديل `isActive`).
5. أعِد المنتج المُقدَّم.

#### 2.3.6 طلبات المورّد — `GET /supplier/orders`

اجلب طلبات `supplierId()` مع `items`، تنازلياً بـ `createdAt`، حد أقصى 100. احلّ أسماء المشترين (المنشآت) في استعلام واحد. أعِد `data` + `meta.total`. اسم المشتري الافتراضي «مغسلة» عند الغياب.

#### 2.3.7 تحديث حالة الطلب — `PATCH /supplier/orders/{id}`

1. تحقّق: `status` ∈ {`CONFIRMED`,`SHIPPED`,`DELIVERED`,`CANCELLED`} (لاحظ أن `PENDING` ليست هدفاً صالحاً).
2. اجلب طلباً بشرط `id` **و** `supplierId = supplierId()`؛ غير موجود → 404.
3. طبّق آلة الحالات: إن لم يكن الهدف ضمن `FLOW[status_current]` → 422 «انتقال غير صالح للحالة».
4. عيّن الحالة الجديدة؛ إن كانت `DELIVERED` اختِم `deliveredAt = now()`.
5. احفظ، أعِد الطلب المُقدَّم مع اسم المشتري.

> بوابة المورّد لا تتيح تعديل العمولة ولا الأسعار على طلب قائم؛ العمولة لقطة ثابتة وقت الإنشاء.

### 2.4 الفئات الثابتة للمنتجات (`MARKET_CATEGORIES`)

مكرَّرة نصياً في كلٍّ من MarketController و SupplierController (مصدر مشترك واحد منطقياً):

## 3. الإعدادات (Settings)

جميع نقاط الإعدادات مقيَّدة بمنشأة المتصل (`orgOrFail` عبر `orgId()`، لا يُقبل معرّف منشأة من العميل).

### 3.1 عرض الإعدادات — `GET /settings`

- **الصلاحية:** `requireManager` (SUPER_ADMIN أو BRANCH_MANAGER).
- يجلب المنشأة ويعيدها مُقدَّمة (present) شاملة: `id, name, defaultCurrency, taxRate, phone, email, address, crNumber, vatNumber, receiptFooter, receiptWidth, brandPrimary, brandAccent, logoUrl, slug, customDomain`.

### 3.2 تحديث الإعدادات التجارية — `PUT /settings`

- **الصلاحية:** `requireSuperAdmin` (مدير المنشأة العام فقط).
- الحقول (ملف المنشأة + الفاتورة + الضريبة + العلامة):

| الحقل | القاعدة |
|------|------|
| `name` | مطلوب، 1..200 |
| `defaultCurrency` | مطلوب، 1..10 |
| `taxRate` | مطلوب، رقم 0..100 |
| `phone` / `email` / `address` / `crNumber` / `vatNumber` / `receiptFooter` | اختيارية؛ **الفراغ يُحوَّل إلى null** (تنظيف الأعمدة) |
| `receiptWidth` | مطلوب ∈ {58, 80} — عرض ورق الإيصال |
| `brandPrimary` / `brandAccent` | اختياري، لون HEX سداسي `#rrggbb`؛ يُطبَّع lowercase أو null عند عدم الصلاحية |

- يحدّث المنشأة مباشرة ويعيد اللقطة الطازجة.

### 3.3 هوية بوابة العميل — `PUT /settings/portal`

- **الصلاحية:** `requireSuperAdmin`.
- تحديث «هوية البوابة والعلامة» في **معاملة واحدة** حتى لا يتباعد مخزنا العمود والإعداد. يلمس حقول البوابة فقط فلا يصطدم بتعديلات الأعمال المتزامنة.
- الحقول:

| الحقل | القاعدة |
|------|------|
| `logoUrl` | اختياري؛ رابط http(s) مطلق أو مسار رفع جذري `/` (يمنع `js:`/`data:`) |
| `slug` | اختياري، 2..40، نمط `^[a-z0-9_-]+$`؛ **فريد** على مستوى `Organization.slug` (مع تجاهل الذات)؛ **ولا يتصادم مع أي `id` منشأة أخرى** (وإلا صار توجيه `resolveOrg` غامضاً بين slug و id — خطر توجيه عبر المستأجرين) |
| `customDomain` | اختياري، حتى 200، نمط `^[a-z0-9.-]+$`، يُطبَّع lowercase |
| `showOffers` | مطلوب منطقي |
| `termsUrl` / `privacyUrl` | اختياري، url http/https حتى 500 |

- داخل المعاملة:
  1. يحدّث `Organization`: `logoUrl` (أو null)، `slug` (**إن مُسِح يُبقي القديم** حتى لا ينكسر رابط بوابة محفوظ)، `customDomain` (lowercase أو null).
  2. يكتب/يحدّث صف `Setting` بالمفتاح `portal.config:{orgId}` (branchId=null) بقيمة `{showOffers, termsUrl, privacyUrl}`؛ id يُولَّد يدوياً (cuid) و`updatedAt` تُختَم يدوياً.
- يعيد لقطة البوابة (presentPortal) دامجاً أعمدة المنشأة مع محتوى `portal.config`.

> **تنبيه ازدواج المفتاح:** المفتاح `portal.config:{orgId}` مشترك بين نقطة `PUT /settings/portal` ومجموعة التكوين `offers` (القسم 4). كلاهما يكتب `showOffers/termsUrl/privacyUrl` في نفس الصف — يجب توخّي الحذر أن أحدهما لا يمحو حقول الآخر (كلاهما يكتب الحقول الثلاثة نفسها فلا فقد حالياً).

## 4. التكوين (Config groups)

مجموعات JSON لكل منشأة تُخزَّن كصفوف `Setting` (branchId=null) بمفتاح `{prefix}.config:{orgId}`، متوافقة بايتياً مع مخزن Next.js.

| المجموعة | البادئة/المفتاح |
|------|------|
| `automation` | `automation.config:{orgId}` |
| `credit` | `credit.config:{orgId}` |
| `offers` | `portal.config:{orgId}` |
| `notifications` | `notifications.config:{orgId}` |

### 4.1 عرض مجموعة — `GET /settings/config/{group}`

- **الصلاحية:** لا بوابة دور صريحة على القراءة (تحت `auth.api` فقط؛ `orgId()` يفرض `assertStaff`). مجموعة غير معروفة → 404.
- يقرأ الصف ويدمجه فوق الافتراضيات عبر `array_replace_recursive` بحيث تُعاد بنية كاملة حتى لو نقص مفتاح جديد من صف قديم.

### 4.2 تحديث مجموعة — `PUT /settings/config/{group}`

- **الصلاحية:** `requireSuperAdmin`. مجموعة غير معروفة → 404.
- يتحقق حسب المجموعة ثم يكتب القيمة الكاملة (writeConfig).

### 4.3 تفاصيل المجموعات والافتراضيات

#### `automation` (أتمتة أزمنة التسليم)

- `enabled` (منطقي، افتراضي false).
- `default`: `{normal, express}` دقائق (افتراضي 180/30).
- `byServiceType`: لكل من `WASH`/`IRON`/`WASH_IRON` قيم `{normal, express}` دقائق (0..100000؛ افتراضي 0/0).
- القيم تُحوَّل لأعداد صحيحة عند الحفظ.

#### `credit` (الآجل)

- `enabled` (منطقي، افتراضي false).
- `defaultLimit` (رقم 0..10,000,000؛ افتراضي 0) — حد الآجل الافتراضي للعملاء.

#### `notifications` (تنبيهات لوحة التحكم)

مفاتيح منطقية مطلوبة كلها: `enabled` (افتراضي true)، `lateOrders` (true)، `deliveryRequests` (true)، `readyOrders` (true)، `onlinePayments` (true)، `unpaidOrders` (**افتراضي false**).

#### `offers` (العروض ومستندات البوابة)

- `showOffers` (منطقي مطلوب).
- `termsUrl` / `privacyUrl` (url http/https حتى 500، تُقلَّم؛ افتراضي فارغ). — يشترك في المفتاح `portal.config:{orgId}` (انظر تنبيه الازدواج في 3.3).

## 5. التكاملات والأسرار (Integrations & secrets)

مجموعة خاصة تجمع طرق الدفع + بوابة الدفع + واتساب + SMS. تُخزَّن في مفتاحين منفصلين: `payment.config:{orgId}` و`messaging.config:{orgId}`. **الأسرار تُشفَّر عبر `SecretValue` ولا تُرسل للمتصفح أبداً.**

### 5.1 مبدأ عدم التسريب (غير قابل للتفاوض)

1. **GET لا يُرجع أسراراً أبداً:** يعيد الأسرار **فارغة** (`''`) ويرفق أعلام `secretsSet` منطقية تخبر الواجهة فقط بأن السر «مضبوط أم لا»:
   - `paySecret` = هل `gateway.secretKey` غير فارغ؟
   - `waToken` = هل `whatsapp.token` غير فارغ؟
   - `smsApiKey` = هل `sms.apiKey` غير فارغ؟
2. **الحفظ يُبقي القديم عند الفراغ:** عند `PUT`، إذا وُرِد سرٌّ فارغاً (بعد trim) **يُحتفَظ بالسر المخزَّن** (دالة `keep`). فلا يمكن للواجهة أن تمحو سراً بإرسال فراغ.
3. **التشفير عند التخزين:** عند القراءة الداخلية (`readConfig`) تُفكّ الأسرار عبر `SecretValue::decrypt`؛ وعند الكتابة (`writeConfig`) تُشفَّر عبر `SecretValue::encrypt` قبل حفظها في `Setting.value`.
4. **العودة الآمنة بعد PUT:** بعد الحفظ يعيد `updateIntegrations` نفس عرض الـ GET (بلا أسرار) لإعادة ترطيب العميل.

### 5.2 آلية `SecretValue` (التشفير)

- غلاف **AES-256-GCM** متوافق مع `secret-store.ts` في laundry-system، ببادئة `enc:v1:` و AAD ثابت `laundry-settings-v1`.
- المفتاح مشتق من `services.settings_encryption_key` عبر `sha256`؛ غيابه → استثناء «SETTINGS_ENCRYPTION_KEY مطلوب».
- `encrypt`: الفراغ يمرّ كما هو؛ إن كانت القيمة غلافاً `enc:v1:` صالحاً يُمرَّر دون إعادة تغليف (منع double-wrap)؛ غلاف مزوَّر/أجنبي يُعامَل كنص عادي ويُشفَّر (حتى لا يُخزَّن blob غير قابل للفك أبداً).
- `decrypt`: بلا بادئة `enc:v1:` → يُعاد كنص عادي (توافق مع نص قديم غير مشفَّر يُشفَّر عند الحفظ القادم)؛ غلاف تالف → استثناء.
- ترميز base64url بلا padding.

### 5.3 عرض التكاملات — `GET /settings/integrations`

- **الصلاحية:** لا بوابة دور صريحة على القراءة (تحت `auth.api`؛ `assertStaff` ضمناً). يعيد `payment` + `messaging` (بأسرار مُفرَّغة) + `secretsSet`.

### 5.4 تحديث التكاملات — `PUT /settings/integrations`

- **الصلاحية:** `requireSuperAdmin`.
- **الدفع (`payment`):**
  - `methods`: أعلام منطقية مطلوبة لكل من `CASH/CARD/TRANSFER/WALLET/DEFERRED` — طرق الدفع المفعّلة في المنشأة.
  - `gateway.provider` ∈ {`stub`,`moyasar`,`hyperpay`}.
  - `gateway.publicKey` (نص، حتى 500).
  - `gateway.secretKey` (سر؛ فارغ = يُبقي القديم).
- **المراسلة (`messaging`):**
  - `enabled` مفتاح رئيسي للمنشأة.
  - `whatsapp`: `enabled` (مطلوب)، `mode` ∈ {`PLATFORM`,`CUSTOM`}، `token` (سر؛ فارغ = يُبقي)، `phoneId`.
  - `events`: مصفوفة أعلام منطقية — **تُحفَظ المفاتيح المعروفة فقط** (من `WaService::EVENTS`: `orderCreated, orderReady, orderCompleted, otp, invoice, delivery, manual, test`) — طبقة المنشأة من بوابة أحداث الرسائل.
  - `sms`: `enabled` (مطلوب)، `provider`، `apiKey` (سر؛ فارغ = يُبقي)، `sender`.
  - `templates`: قوالب نصية `orderReady`, `otp`, `paymentLink`, `winBack` (كلٌّ يعود لقيمته المخزَّنة عند الغياب).
- يكتب المفتاحين ثم يعيد عرض الـ GET الآمن.

### 5.5 الافتراضيات

- **دفع افتراضي:** كل الطرق مفعّلة، `gateway = {provider:'stub', publicKey:'', secretKey:''}`.
- **مراسلة افتراضية:** من `WaService::defaultConfig()` — `enabled:true`، واتساب معطّل (`mode:'PLATFORM'`)، SMS معطّل (`sender:'Laundry'`)، أحداث افتراضية (`orderReady/otp/invoice/delivery = true`، الباقي false)، قوالب افتراضية.

## 6. سجل التدقيق (AuditLog)

### 6.1 الكيان `AuditLog` — جدول `AuditLog`

سجل **غير قابل للتعديل** (append-only) للإجراءات المميّزة. له `createdAt` بلا `updatedAt`؛ الطوابع معطّلة والكتابة تختم `createdAt` يدوياً. النموذج محمي من mass-assignment (يُكتَب عبر `forceCreate` من كاتب موثوق فقط).

| الحقل | النوع | الوصف |
|------|------|------|
| `id` | نص (cuid) | المفتاح الأساسي |
| `userId` | نص | المستخدم الفاعل (قد يكون null) |
| `action` | نص | نوع الإجراء (انظر 6.2) |
| `entity` | نص | اسم الكيان (Payable/Budget/Asset/…) |
| `entityId` | نص | معرّف السجل المتأثّر |
| `before` | JSON | لقطة ما قبل التغيير (null للإنشاء) |
| `after` | JSON | لقطة ما بعد التغيير (null للحذف) |
| `ip` | نص | عنوان IP للفاعل |
| `createdAt` | تاريخ | وقت الحدث (مختوم يدوياً) |

> **لا يحوي `AuditLog` عمود `orgId`** — لذا العزل عبر المنشأة يتم استدلالاً عبر مستخدمي المنشأة (انظر 6.3).

### 6.2 مستويات/أنواع الإجراءات (`action`)

الكاتب `AuditTrail::log` يوثّق قيم `action` مثل: `CREATE`, `UPDATE`, `DELETE`, `PAY`, `VOID`, `REORDER`، وغيرها (نصية حرة يحددها المستدعي). الكتابة عبر مختلف مراقبي المالية/العمليات (`AuditTrail` عبر الكودبيس). فشل التدقيق **لا يُفشِل** إجراء العمل (يُلتقَط ويُبلَّغ عبر `report()`).

### 6.3 عرض السجل — `GET /audit`

- **الصلاحية:** SUPER_ADMIN فقط عبر بوابة داخلية `gate()` تفحص `claims.role === 'SUPER_ADMIN'` (403 «سجل التدقيق متاح لمدير المنشأة العام فقط»).
- **آلية العزل عبر UserBranch:** بما أن الجدول بلا orgId، يُحسَب نطاق المستأجر هكذا:
  1. `orgUserIds`: كل فروع المنشأة (`Branch.where(orgId)`) → كل مستخدمي هذه الفروع عبر `UserBranch` (distinct userId).
  2. تُقيَّد كل الاستعلامات بـ `whereIn('userId', $userIds)`.
- **الفلاتر:** `entity`، `action`، `from`/`to` (تواريخ تُحلَّل بأمان: مدخل مشوّه → null بلا 500؛ `from` من بداية اليوم، `to` حتى نهاية اليوم)، `limit` (يُقصَر بين 1 و500، افتراضي 100).
- **الترتيب:** تنازلي بـ `createdAt`.
- **الإثراء:** حلّ أسماء المستخدمين (`User.name`) في استعلام واحد.
- **الواجهات (facets):** يعيد قوائم `entities` و`actions` المميّزة التي أنتجتها هذه المنشأة (للفلترة في الواجهة).
- يعيد `data[]` (كل حقول السجل بما فيها before/after/ip) + `meta{count, limit, entities, actions}`.

> السجل **للقراءة فقط** عبر الـ API؛ لا توجد نقطة إنشاء/تعديل/حذف مكشوفة — الكتابة داخلية عبر `AuditTrail` فقط.

## 7. OrgStore ونمط التخزين (ملاحظة لإعادة البناء)

### 7.1 النمط

`App\Support\OrgStore` هو مخزن JSON لكل مستأجر مبني فوق جدول `Setting` الموجود — الطريقة المعتمدة في المشروع لتخزين كيانات جديدة **دون أي تغيير في المخطط** (القاعدة المشتركة عبر Prisma مجمّدة DDL).

- **نمط المفاتيح:** `"{type}:{orgId}:{id}"` — فكل قراءة معزولة بالمنشأة عبر البادئة، والـ JSON الخام في `Setting.value`.
- `Setting` نموذج عادي (بلا cuid boot ولا timestamps) فيُدار `id` (عبر `PrismaModel::newCuid()`) و`updatedAt` يدوياً.
- **العمليات:**
  - `put(type, orgId, id, value, branchId=null)`: إنشاء/استبدال سجل، يعيد القيمة مع `id`.
  - `get(type, orgId, id)`: قيمة واحدة (مع `id` و`_branchId` و`_updatedAt`) أو null.
  - `all(type, orgId)`: كل سجلات النوع للمنشأة كقائمة (كلٌّ بمعرّفه) عبر `LIKE 'prefix%'`.
  - `orgIds(type)`: كل معرّفات المنشآت التي لها سجل من هذا النوع (لِـcron sweeps).
  - `forget(type, orgId, id)`: حذف.

### 7.2 ملاحظة إعادة البناء النظيفة

> **هذا نمط جسر (workaround) مفروض بقيد «الإضافة فقط» على قاعدة Prisma المشتركة.** في البناء النظيف يجب أن تتحول هذه البيانات إلى **جداول حقيقية** بدل صفوف key/value في `Setting`:
> - مجموعات التكوين (`automation`, `credit`, `notifications`, `offers`/`portal`) → جداول إعدادات مُهيكَلة أو أعمدة مخصصة على المنشأة.
> - أسرار التكامل (`payment.config`, `messaging.config`) → جدول أسرار مخصص مع تشفير على مستوى العمود.
> - أي بيانات `OrgStore` (`{type}:{orgId}:{id}`) → جداول كيانات فعلية مفهرَسة بـ `orgId` بدل `LIKE` على المفتاح (الذي لا يستفيد من الفهارس ويتدهور مع النمو).
>
> يُنصَح في البناء النظيف بترحيل صفوف `Setting` هذه إلى الجداول الجديدة وإسقاط نمط المفتاح النصي.

## 8. قواعد البيزنس (مرقّمة)

1. **السوق ميزة خطة:** كل نقاط جانب المشتري تتطلب ميزة `supplier_market` (403/402 حسب الحالة عند غيابها).
2. **الظهور للمشتري = APPROVED فقط:** لا يظهر منتج في التصفّح أو يُقبل في طلب إلا إن كان `isActive=true` ومورّده `status=APPROVED`.
3. **سلة = مورّد واحد:** كل طلب سوق لمورّد واحد؛ خلط موردين → رفض 422.
4. **توافر المنتجات:** أي منتج مطلوب غير متاح (غير نشط/مورّد غير معتمد/غير موجود) → رفض الطلب كاملاً 422.
5. **دمج المكرّرات:** تُجمَّع كميات نفس المنتج قبل الحساب.
6. **العمولة PERCENT الافتراضية 8%** عند غياب قيمة المورّد.
7. **FIXED مسقوفة بالإجمالي:** لا تتجاوز العمولة الثابتة `subtotal`.
8. **SUBSCRIPTION بلا عمولة لكل طلب** (`commissionAmount=0`).
9. **المشتري يدفع الإجمالي كاملاً:** `total = subtotal`؛ العمولة تُخصَم من `supplierPayout = subtotal − commissionAmount` فقط، لا تُضاف على المشتري.
10. **لقطات الأسطر ثابتة:** name/unit/unitPrice تُخزَّن snapshot وقت الطلب فلا تتأثر بتغيّر المنتج لاحقاً.
11. **العمولة لقطة وقت الإنشاء:** `commissionType/Rate/Amount` تُثبَّت على الطلب ولا تتغير بتغيّر إعداد المورّد لاحقاً.
12. **آلة حالات المورّد صارمة:** الانتقالات فقط ضمن `SUPPLIER_FLOW`؛ أي انتقال آخر 422. `DELIVERED`/`CANCELLED` نهائية.
13. **ختم التسليم:** `deliveredAt` يُختَم فقط عند الانتقال إلى `DELIVERED`.
14. **حصر المورّد على مورّده:** كل منتجات/طلبات بوابة المورّد مقيَّدة بـ `supplierId` من التوكن؛ محاولة الوصول لمورد آخر → 404.
15. **حصر المشتري على منشأته:** كل طلبات جانب المشتري مقيَّدة بـ `orgId` من التوكن.
16. **دخول المورّد:** REJECTED محظور (403)؛ PENDING/SUSPENDED مسموح مع شارة حالة؛ رسالة فشل موحّدة لا تميّز البريد عن كلمة المرور.
17. **توكن المورّد منفصل:** `kind=supplier` لمدة 30 يوماً؛ توكن طاقم/عميل مرفوض على نقاط المورّد والعكس صحيح.
18. **كلمات المرور عبر `password_verify`** لا `Hash::check`.
19. **passwordHash لا يُسلسَل أبداً** (`$hidden` على `MarketSupplier`).
20. **تحديث الإعدادات التجارية = SUPER_ADMIN فقط؛ العرض = Manager.**
21. **الحقول الاختيارية الفارغة → null** (تنظيف الأعمدة) في الإعدادات التجارية.
22. **`receiptWidth` ∈ {58,80}** حصراً.
23. **ألوان العلامة HEX سداسي** يُطبَّع lowercase أو يُهمَل.
24. **تحديث البوابة ذرّي:** أعمدة المنشأة + `portal.config` في معاملة واحدة؛ **slug ممسوح يُبقي القديم**.
25. **slug فريد وغير متصادم مع أي id منشأة** (منع غموض التوجيه عبر المستأجرين).
26. **logoUrl مقيَّد بنمط** يمنع `js:`/`data:` (http(s) مطلق أو مسار جذري).
27. **الأسرار لا تُرسل للمتصفح أبداً:** GET يعيدها فارغة مع `secretsSet` منطقية.
28. **الحفظ يُبقي السر القديم عند إرسال فراغ** — لا يمكن مسح سرّ بإرسال قيمة فارغة.
29. **الأسرار مشفّرة عند التخزين** عبر `SecretValue` (AES-256-GCM، بادئة `enc:v1:`)؛ غياب مفتاح التشفير → استثناء.
30. **منع double-wrap** للأغلفة الصالحة، ورفض تخزين غلاف مزوّر verbatim.
31. **أحداث الرسائل المعروفة فقط تُحفَظ** (تُصفّى عبر `WaService::EVENTS`).
32. **تحديث التكوين/التكاملات = SUPER_ADMIN؛** القراءة بلا بوابة دور صريحة (طاقم فقط ضمناً).
33. **مجموعة تكوين غير معروفة → 404.**
34. **القراءة تدمج فوق الافتراضيات** فتُعاد بنية كاملة دائماً حتى لصف قديم ناقص المفاتيح.
35. **سجل التدقيق SUPER_ADMIN فقط.**
36. **عزل التدقيق عبر UserBranch:** لا orgId في الجدول، فالنطاق = مستخدمو فروع المنشأة.
37. **التدقيق للقراءة فقط**، append-only، والكتابة داخلية عبر `AuditTrail` (forceCreate) لا تُفشِل إجراء العمل عند فشلها.
38. **`limit` التدقيق مقصور 1..500** (افتراضي 100)، وتواريخ مشوّهة تُتجاهَل بلا 500.
39. **OrgStore معزول بالبادئة** `{type}:{orgId}:` لكل قراءة.

## 10. حالات خاصة وفجوات

1. **ازدواج مفتاح `portal.config:{orgId}`:** يكتبه كلٌّ من `PUT /settings/portal` ومجموعة `offers`؛ الحقول متطابقة (`showOffers/termsUrl/privacyUrl`) فلا فقد حالياً، لكن أي إضافة حقل لأحدهما دون الآخر قد تمحوه. **فجوة صيانة.**
2. **قراءة التكوين/التكاملات بلا بوابة دور صريحة:** GET على `config`/`integrations` متاحة لأي عضو طاقم (بما فيهم الكاشير)، بينما GET على `/settings` تتطلب Manager. عدم اتساق يستحق المراجعة — رغم أن التكاملات لا تسرّب أسراراً.
3. **الفئات الثابتة مكرّرة نصياً** في MarketController و SupplierController؛ لا مصدر مشترك واحد — خطر انحراف مستقبلي.
4. **`total = subtotal` بلا ضريبة/شحن:** لا يحسب مسار السوق أي ضريبة أو رسوم شحن على المشتري.
5. **علَما `inventoryApplied`/`accountingPosted` غير مكتوبين:** موجودان في الكاست لكن لا يُحدَّثهما المسار الحالي — الطلبات لا تُرحَّل محاسبياً ولا تُطبَّق على المخزون تلقائياً هنا (لا تكامل مالي/مخزني للسوق حتى الآن).
6. **لا مسار دفع فعلي لطلبات السوق:** `paymentStatus` يبدأ `UNPAID` ولا نقطة تُبدّله إلى `PAID`؛ تسوية المستحقات خارج هذا المجال.
7. **لا حذف منتجات المورّد:** فقط إنشاء/تحديث (والإيقاف عبر `isActive`)؛ لا نقطة DELETE.
8. **لا تدقيق (AuditLog) لتغييرات السوق/الإعدادات:** الكتابة عبر `AuditTrail` مبثوثة في مراقبي المالية/العمليات؛ لكن لا يظهر استدعاؤها في متحكمات هذا المجال (السوق/الإعدادات/التكوين/التكاملات لا تكتب سجل تدقيق) — **فجوة تدقيق**.
9. **عزل التدقيق يعتمد على UserBranch:** مستخدم بلا أي `UserBranch` لن تظهر أفعاله في سجل منشأته؛ ومستخدم منقول بين منشآت قد تختلط رؤيته — قيد بنيوي لغياب `orgId` في `AuditLog`.
10. **`slug` ممسوح يبقي القديم لكن `customDomain`/`logoUrl` الممسوحان يصبحان null** — سلوك غير متماثل مقصود (حماية الرابط فقط).
11. **لا bootstrap لحساب المورّد:** لا نقطة تسجيل مورّد جديد في هذا المجال (التسجيل/الاعتماد يتم عبر لوحة المنصة/مسار آخر)؛ البوابة هنا للدخول والإدارة فقط.
12. **حدود القوائم ثابتة:** منتجات السوق 200، طلبات المنشأة/المورّد 100 — بلا ترقيم صفحات (pagination)؛ تدهور محتمل مع النمو.
13. **`OrgStore`/`Setting` عبر `LIKE 'prefix%'`** لا يستفيد من الفهارس — أداء يتدهور مع كثرة الصفوف (انظر ملاحظة إعادة البناء 7.2).
14. **مفتاح التشفير مطلوب حصراً:** غياب `SETTINGS_ENCRYPTION_KEY` يجعل قراءة/كتابة أي تكامل تُلقي استثناءً — يجب ضمانه في البيئة قبل استخدام التكاملات.
