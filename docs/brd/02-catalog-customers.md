# BRD 02 — الكتالوج والعملاء

> يفترض هذا الملف أن القارئ قرأ `00-overview-architecture.md` (المصادقة بتوكن HMAC، سِمة `ResolvesTenant`، نموذج PrismaModel بمعرّفات cuid نصية، عزل المستأجرين عبر `orgId`/`branchId`، تخزين الإعدادات في جدول `Setting` كـ key/value).

---

## 1. نظرة عامة

هذا المجال يغطي **قائمة الأسعار (الكتالوج)** التي يبيع منها الكاشير في نقطة البيع، و**سجل العملاء** الذين تُنسب إليهم الطلبات والمحافظ والاشتراكات، بالإضافة إلى **نظام الآجل/الائتمان** للعميل.

الكتالوج مبني على **نموذج ثلاثي المستويات (three-dimension model)**:

```
ServiceCategory (تصنيف)  →  Product (منتج/قطعة)  →  Service (خلية سعر لكل نوع خدمة)
   مثال: "ملابس رجالية"        "ثوب"                   ثوب × غسيل    = 5 ريال
                                                        ثوب × كوي     = 3 ريال
                                                        ثوب × غسيل وكوي = 7 ريال
```

كل **Service** هو "خلية سعر" واحدة تربط منتجاً بنوع خدمة واحد (`WASH` / `IRON` / `WASH_IRON`) وتحمل سعرها الأساسي ورسوم الاستعجال. الكنترولر المسؤول عن الكتالوج بأكمله هو `CatalogController`. المصدر الأصلي (Next.js) هو `src/server/catalog.ts` (الدالة `getPosCatalog`)، والكود هنا يحاكيه بدقة.

سجل العملاء يديره `CustomerController`، وعناوين التوصيل (`CustomerAddress`) يديرها بوابة العميل (`PortalController`) وليس طاقم المنشأة. أنواع القطع (`GarmentType`) ووحدات القياس (`Unit`) كيانات مرجعية للقراءة فقط في هذا الـ API (لا توجد لها نقاط CRUD هنا).

**نطاق التعديل:** كل عمليات الكتالوج والعملاء مقيّدة بمنشأة المستدعي (`orgId`). عمليات القراءة تحترم رأس `X-Branch-Id` عبر `branchIds()`.

## 2. كيانات الكتالوج

### 2.1 ServiceCategory (التصنيف)

جدول `ServiceCategory` — كيان Prisma **بلا timestamps** (`public $timestamps = false`). المعرّف cuid نصي.

| الحقل | النوع | Nullable / افتراضي | المعنى |
|---|---|---|---|
| `id` | string (cuid) | PK، يُولّد بـ `PrismaModel::newCuid()` | المعرّف الفريد |
| `orgId` | string | مطلوب | المنشأة المالكة (عزل المستأجر) |
| `name` | string (≤191) | مطلوب | الاسم العربي المعروض (مثال: "ملابس رجالية") |
| `nameEn` | string (≤191) | nullable | الاسم الإنجليزي (اختياري، POS يتجاهله) |
| `icon` | string (≤191) | nullable | أيقونة/رمز العرض |
| `sortOrder` | integer | افتراضي عند الإنشاء = آخر الترتيب | ترتيب الظهور تصاعدياً |
| `isActive` | boolean | افتراضي `true` | نشط/معطّل — التعطيل يخفيه من POS ولا يحذفه |

**العلاقات:** `hasMany Product` (عبر `categoryId`)، `hasMany Service` (عبر `categoryId`).

### 2.2 Product (المنتج / القطعة)

جدول `Product` — كيان Prisma **بلا timestamps**.

| الحقل | النوع | Nullable / افتراضي | المعنى |
|---|---|---|---|
| `id` | string (cuid) | PK | المعرّف الفريد |
| `orgId` | string | مطلوب | المنشأة المالكة |
| `categoryId` | string | مطلوب | التصنيف الأب |
| `name` | string (≤191) | مطلوب | اسم القطعة (مثال: "ثوب") |
| `nameEn` | string (≤191) | nullable | الاسم الإنجليزي |
| `icon` | string (≤191) | nullable | أيقونة العرض |
| `code` | string (≤64) | nullable | **رمز المنتج (الباركود/الكود الداخلي)** — يُحرَّر بصلاحية مستقلة `catalog.manageCodes` |
| `sortOrder` | integer | افتراضي = آخر الترتيب داخل التصنيف | ترتيب الظهور |
| `isActive` | boolean | افتراضي `true` | نشط/معطّل |

**العلاقات:** `belongsTo ServiceCategory` (عبر `categoryId`)، `hasMany Service` (عبر `productId`).

### 2.3 Service (خلية السعر)

جدول `Service` — كيان Prisma **بلا timestamps**. يمثّل **خلية سعر واحدة**: منتج × نوع خدمة. جدول `OrderItem` يشير إلى `serviceId`، ولذلك **تُعطَّل الخلايا (`isActive=false`) بدلاً من حذفها** بمجرد أن ترتبط بطلبات.

| الحقل | النوع | Nullable / افتراضي | المعنى |
|---|---|---|---|
| `id` | string (cuid) | PK | معرّف الخلية (يُخزَّن في `OrderItem.serviceId`) |
| `orgId` | string | مطلوب | المنشأة المالكة |
| `categoryId` | string | مطلوب | التصنيف (منسوخ من المنتج) |
| `productId` | string | مطلوب | المنتج الأب |
| `serviceType` | enum | مطلوب | **نوع الخدمة** (انظر أدناه) |
| `name` | string | مطلوب | الاسم (مطابق لاسم المنتج؛ يُزامَن عند إعادة تسمية المنتج) |
| `nameEn` | string | nullable | الاسم الإنجليزي |
| `pricingType` | enum | افتراضي `PER_PIECE` عند الإنشاء | **طريقة التسعير** (انظر أدناه) |
| `basePrice` | float | مطلوب (≥0) | السعر الأساسي (العادي) |
| `expressSurcharge` | float | افتراضي `0` | رسوم الاستعجال المضافة فوق السعر الأساسي |
| `isExpressAvailable` | boolean | افتراضي `true` | هل الاستعجال متاح لهذه الخلية |
| `isActive` | boolean | افتراضي `true` | نشط/معطّل |

**السعر المعروض في POS:**
- السعر العادي = `basePrice`
- سعر الاستعجال = `basePrice + expressSurcharge`
كلاهما مقرَّب لخانتين عشريتين.

#### enum: `serviceType` (نوع الخدمة)

القيم المسموحة الثلاث فقط، وترتيب أزرارها في POS ثابت هكذا:

| القيمة | المعنى | ترتيب الزر في POS |
|---|---|---|
| `WASH_IRON` | غسيل وكوي | 1 (الأول) |
| `IRON` | كوي فقط | 2 |
| `WASH` | غسيل فقط | 3 |

الثابت `TYPE_ORDER = ['WASH_IRON', 'IRON', 'WASH']` في الكنترولر هو مصدر هذا الترتيب. أي نوع خدمة غير هذه الثلاثة يُتجاهَل عند إنشاء المنتج (`array_intersect_key`).

#### enum: `pricingType` (طريقة التسعير)

القيمة الوحيدة التي ينتجها هذا الـ API عند الإنشاء هي `PER_PIECE` (تسعير بالقطعة). العمود عبارة عن Postgres enum؛ القيم الأخرى (مثل تسعير بالوزن) قد تكون موجودة تاريخياً من نظام Next.js لكن مسار إنشاء المنتج هنا يثبّتها دائماً على `PER_PIECE`. تُعاد `pricingType` في استجابة الكتالوج ليعرضها POS.

### 2.4 GarmentType (نوع القطعة)

جدول `GarmentType` — كيان Prisma **بلا timestamps**. يمثّل نوع الملبس (ثوب / قميص / بنطال …). يشير إليه `OrderItem.garmentTypeId` ويُستخدم لإثراء وصف بند الفاتورة.

- **لا توجد نقاط CRUD في هذا الـ API** لإدارة أنواع القطع. يُقرأ فقط (بالاسم عبر `whereIn('id', …)->pluck('name','id')`) داخل `OrderDetailController` و`PortalController` و`ZatcaController` و`ZatcaPhase2Controller` لتسمية بنود الفاتورة/الطلب.
- إدارته تتم من نظام Next.js الأصلي أو عبر seed. (فجوة — انظر القسم 9.)

### 2.5 Unit (وحدة القياس)

جدول `Unit` — كيان Prisma **بلا timestamps**. وحدة قياس المخزون (قطعة / لتر / كيلو)، مقيّدة بمنشأة.

| الحقل | النوع | Nullable / افتراضي | المعنى |
|---|---|---|---|
| `id` | string (cuid) | PK | المعرّف |
| `orgId` | string | مطلوب | المنشأة المالكة |
| `name` | string | مطلوب | اسم الوحدة (مثال: "لتر") |
| `symbol` | string | — | الرمز (مثال: "L") |
| `conversionFactor` | float | — | معامل التحويل للوحدة الأساسية |

**العلاقات:** `hasMany InventoryItem` (عبر `unitId`).

- **لا توجد نقاط CRUD للوحدات في مجال الكتالوج**؛ تُقرأ وتُتحقَّق داخل `InventoryController` (مجال المخزون). إدراجها هنا لأن أصل الطلب طلب كيان `Unit`. تفاصيلها الكاملة في مجال المخزون.

## 3. كيانات العملاء

### 3.1 Customer (العميل)

جدول `Customer` — كيان Prisma **مع timestamps** (`createdAt`/`updatedAt` مُدارة). المعرّف cuid نصي.

| الحقل | النوع | Nullable / افتراضي | المعنى |
|---|---|---|---|
| `id` | string (cuid) | PK | المعرّف الفريد |
| `orgId` | string | مطلوب | المنشأة المالكة (نطاق تفرّد الهاتف) |
| `branchId` | string | مطلوب (فرع الإنشاء) | الفرع الذي أُنشئ فيه العميل (نطاق قراءة القوائم) |
| `name` | string (2–200) | مطلوب | اسم العميل — **مقيَّد الطول** لأنه يُنسخ حرفياً إلى XML فاتورة ZATCA وقوالب واتساب |
| `phone` | string (6–32) | مطلوب | رقم الهاتف — **فريد داخل المنشأة الواحدة فقط** |
| `email` | string (≤200) | nullable (يُطبَّع الفارغ إلى null) | البريد الإلكتروني |
| `address` | string (≤500) | nullable | عنوان نصّي حر (حقل مفرد؛ يختلف عن `CustomerAddress` المنظّم) |
| `birthDate` | datetime | nullable | تاريخ الميلاد (لعروض أعياد الميلاد) |
| `type` | enum | مطلوب | **نوع العميل** (انظر أدناه) |
| `creditLimit` | float | nullable (≥0) | **السقف الائتماني** للآجل (انظر القسم 5) |
| `walletBalance` | float | افتراضي 0 (لا يُكتب من هنا) | رصيد المحفظة — **إشارة فقط**؛ كل حركاته عبر `WalletService` (تفاصيله في ملف المدفوعات) |
| `preferences` | array/json | nullable | تفضيلات العميل (JSON) |

#### enum: `type` (نوع العميل)

| القيمة | المعنى |
|---|---|
| `REGULAR` | عميل عادي |
| `VIP` | عميل مميّز |
| `CORPORATE` | عميل مؤسسي/شركة |

أي قيمة أخرى تُرفَض في الإنشاء/التعديل (`Rule::in`)، وفي فلتر القائمة تُتجاهَل القيمة غير المعروفة (لتفادي خطأ enum على مستوى قاعدة البيانات).

**العلاقات:** `hasMany Order` (عبر `customerId`). كذلك يرتبط منطقياً بـ `LoyaltyAccount` و`Subscription` و`CustomerAddress` (تُقرأ في صفحة العميل).

**قيود مالية:** لا يجوز قراءة `walletBalance` وكتابته يدوياً — كل حركة محفظة تمر عبر `WalletService::credit/debit` الذي يأخذ قفلاً `FOR UPDATE` على صف العميل. (مفصّل في ملف المدفوعات.)

### 3.2 CustomerAddress (عنوان التوصيل)

جدول `CustomerAddress` — كيان Prisma فيه `createdAt` (افتراضي من قاعدة البيانات) **بلا `updatedAt`** (`const UPDATED_AT = null`). يُحذف تتابعياً (cascade) مع العميل.

| الحقل | النوع | Nullable / افتراضي | المعنى |
|---|---|---|---|
| `id` | string (cuid) | PK | المعرّف |
| `customerId` | string | مطلوب | العميل المالك |
| `label` | string (≤40) | مطلوب | تسمية العنوان (مثال: "المنزل"، "العمل") |
| `district` | string (≤80) | nullable | الحي |
| `street` | string (≤160) | nullable | الشارع |
| `details` | string (≤200) | nullable | تفاصيل إضافية |
| `isDefault` | boolean | افتراضي false | هل هو العنوان الافتراضي (**واحد فقط لكل عميل**) |
| `createdAt` | datetime | افتراضي من DB | تاريخ الإنشاء (يُستخدم للترتيب) |

**العلاقة:** `belongsTo Customer`. الترتيب دائماً: الافتراضي أولاً، ثم الأحدث إنشاءً.

**من يديره:** بوابة العميل نفسه (`PortalController`) — وليس طاقم المنشأة. العميل يضيف/يحذف عناوينه الخاصة فقط (مقيَّد بـ `customerId` من توكن البوابة). تعيين عنوان كافتراضي يُلغي الافتراضي السابق داخل نفس المعاملة (transaction) لضمان عدم وجود عنوانين افتراضيين أو صفر عناوين افتراضية.

## 4. قدرات الكتالوج

### 4.1 عرض الكتالوج — `GET /catalog`

يبني قائمة POS الكاملة للمنشأة. الخطوات:

1. جلب كل التصنيفات **النشطة** للمنشأة، مرتّبة بـ `sortOrder` ثم `name`.
2. لكل تصنيف: جلب منتجاته **النشطة** (مرتّبة بـ `sortOrder` ثم `name`) مع خلاياها (`services`) النشطة فقط.
3. لكل منتج: بناء خريطة `cells` مفتاحها `serviceType`، وكل خلية تحمل `serviceId`، `normal` (=`basePrice`)، `express` (=`basePrice+expressSurcharge`)، `pricingType`، `isExpressAvailable`.
4. **تصفية:** يُستبعَد أي منتج ليس له خلايا نشطة، وأي تصنيف ليس له منتجات ذات خلايا.
5. `serviceTypes`: أنواع الخدمة الحاضرة فعلاً عبر كل الكتالوج، مرتّبة حسب `TYPE_ORDER`.
6. `combinedPricingMode`: يُقرأ من `Setting` بمفتاح `catalog.config:{orgId}` — القيمة `'sum'` إن كانت كذلك، وإلا `'independent'` (الافتراضي). يحدّد كيف يجمع POS سعر خدمتين مركّبتين.
7. `taxRate`: نسبة ضريبة المنشأة (`Organization.taxRate`)، افتراضي 15 إن لم تُضبط.
8. `allCategories`: **كل** تصنيفات المنشأة النشطة حتى التي بلا منتجات بعد — لتتمكن صفحة إدارة الكتالوج من إدراج/إعادة ترتيب تصنيف جديد فوراً.

**الصلاحية:** أي طاقم مصادَق (`auth.api` + `assertStaff` ضمنياً عبر `orgId()`). قراءة فقط.

### 4.2 تعديل خلية سعر — `PUT /catalog/services/{id}`

يحدّث `basePrice` و`expressSurcharge` لخلية واحدة (كلاهما مطلوب، ≥0)، مقيّداً بمنشأة المستدعي (خلية من منشأة أخرى → 404). يعيد السعرين المحسوبين.

**الصلاحية:** `requireManager` (SUPER_ADMIN أو BRANCH_MANAGER).

### 4.3 إنشاء تصنيف — `POST /catalog/categories`

ينشئ تصنيفاً جديداً مملوكاً للمنشأة **في نهاية القائمة** (`sortOrder = max+1`، أو 0 إن كان أول تصنيف)، `isActive=true`. يقبل `name` (مطلوب)، `nameEn`، `icon`.

**الصلاحية:** `requireManager`.

### 4.4 تعديل تصنيف — `PATCH /catalog/categories/{id}`

يعدّل `name`/`nameEn`/`icon`/`isActive` (كلها اختيارية) لتصنيف من نفس المنشأة (وإلا 404). **تعيين `isActive=false` هو "تعطيل" التصنيف** (يختفي من POS دون حذف).

**الصلاحية:** `requireManager`.

### 4.5 إعادة ترتيب التصنيفات — `POST /catalog/categories/reorder`

يستقبل مصفوفة `ids` (فريدة، غير فارغة)، ويضبط `sortOrder` لكل معرّف = **موقعه في المصفوفة**، داخل معاملة واحدة. يتحقق أولاً أن **كل** المعرّفات مملوكة للمنشأة (عددها المملوك = عدد المُرسَل)، وإلا 404 (يمنع إعادة ترتيب/لمس تصنيف منشأة أخرى).

**الصلاحية:** `requireManager`.

### 4.6 إنشاء منتج + خلايا — `POST /catalog/products`

ينشئ منتجاً **وصف Service واحد لكل نوع خدمة مُرسَل**، في **معاملة واحدة**. الخطوات:

1. التحقق: `categoryId`, `name` مطلوبان؛ لكل نوع في `cells` (WASH/IRON/WASH_IRON) يجب `basePrice` (مطلوب مع وجود المفتاح، ≥0)، و`expressSurcharge` و`isExpressAvailable` اختياريان.
2. تصفية `cells` على الأنواع الثلاثة المعروفة فقط؛ إن لم يبقَ ولا نوع → خطأ "مطلوب نوع خدمة واحد على الأقل".
3. التأكد أن التصنيف من نفس المنشأة (وإلا 404).
4. إنشاء `Product` في نهاية ترتيب التصنيف (`sortOrder = max+1`)، `isActive=true`.
5. لكل خلية: إنشاء `Service` بـ `serviceType`، `name` = اسم المنتج، `pricingType='PER_PIECE'`، `basePrice`، `expressSurcharge` (افتراضي 0)، `isExpressAvailable` (افتراضي true)، `isActive=true`.

**الصلاحية:** `requireManager`.

### 4.7 تعديل منتج — `PATCH /catalog/products/{id}`

يعدّل `name`/`nameEn`/`icon`/`isActive` (اختيارية) لمنتج من نفس المنشأة (وإلا 404). **إعادة التسمية تزامن اسم كل خلايا (`Service`) المنتج** داخل معاملة واحدة (`Service.name = name`). تعطيل المنتج (`isActive=false`) يخفيه من POS دون حذف.

**الصلاحية:** `requireManager`.

### 4.8 تعديل رمز المنتج — `PATCH /catalog/products/{id}/code`

يعدّل حقل `code` (الرمز/الباركود، ≤64، يقبل null/فارغ ويطبّع الفارغ إلى null) لمنتج من نفس المنشأة.

**الصلاحية:** `catalog.manageCodes` — **صلاحية دقيقة مستقلة** (وليست دور المدير). صُمّمت لتُمنَح لموظف بعينه لإدارة الأرقام/الرموز دون منحه تعديل الكتالوج العام. هذا هو الفرق الجوهري: تعديل الأسعار/التصنيفات/المنتجات يتطلب دور مدير، بينما تعديل الرمز يتطلب هذه الصلاحية بالتحديد.

### 4.9 إعادة ترتيب المنتجات — `POST /catalog/products/reorder`

يستقبل `categoryId` و`ids`؛ يتحقق أن التصنيف من المنشأة، وأن كل المنتجات مملوكة للمنشأة **وتحت هذا التصنيف** (عدد المملوك = عدد المُرسَل، وإلا 404)، ثم يضبط `sortOrder` = الموقع في المصفوفة، داخل معاملة.

**الصلاحية:** `requireManager`.

### 4.10 قاعدة التعطيل بدل الحذف

**لا يوفّر الـ API أي مسار حذف (DELETE) لتصنيف أو منتج أو خلية.** الإزالة الوحيدة المتاحة هي التعطيل (`isActive=false`)، لأن `OrderItem.serviceId` يشير إلى `Service`؛ حذف خلية مرجوعة من طلب سابق يكسر سلامة السجل. هذه قاعدة معمارية صريحة (تعليق في نموذج `Service`).

## 5. قدرات العملاء

### 5.1 إنشاء عميل — `POST /customers`

يتحقق من الحقول (انظر 3.1)، ويرفض **الهاتف المكرَّر داخل نفس المنشأة** (رسالة "رقم الهاتف مسجّل مسبقاً"، 422). يُطبَّع الفارغ في `email`/`address`/`birthDate` إلى null. يُنشأ العميل بـ `orgId` = منشأة المستدعي و`branchId` = فرع المستدعي.

**الصلاحية:** `customers.manage`.

### 5.2 تعديل عميل — `PUT /customers/{id}`

يعدّل عميلاً من نفس المنشأة (وإلا 404)، بنفس تحقق الإنشاء وفحص تكرار الهاتف (مع استثناء معرّف العميل الحالي).

**الصلاحية:** `customers.manage`.

### 5.3 حذف عميل — `DELETE /customers/{id}`

يحذف عميلاً من نفس المنشأة، **لكن يُرفَض الحذف إن كان للعميل أي طلبات سابقة** (رسالة "لا يمكن حذف عميل له طلبات سابقة"، 422) — لعدم تيتيم سجل الطلبات.

**الصلاحية:** `customers.manage`.

### 5.4 قائمة العملاء — `GET /customers`

عملاء المنشأة (ضمن الفروع المسموح قراءتها)، الأحدث تحديثاً أولاً، **بحد أقصى 100**. فلاتر اختيارية:
- `q`: بحث بالاسم (`ilike`) أو الهاتف (`like`).
- `type`: أحد `REGULAR`/`VIP`/`CORPORATE` (غير المعروف يُتجاهَل).

لكل عميل يُحسب في استعلام مجمّع واحد: `unpaidCount` (عدد السلال غير المدفوعة) و`outstanding` (إجمالي المتبقّي = المجموع لكل الطلبات غير الملغاة ذات حالة الدفع `UNPAID`/`PARTIAL`/`DEFERRED`، بمقدار `grandTotal − paidTotal`). يُعيد أيضاً حقول العميل الأساسية بما فيها `walletBalance` و`creditLimit`.

**الصلاحية:** طاقم مصادَق (قراءة).

### 5.5 تفاصيل عميل — `GET /customers/{id}`

صفحة العميل الكاملة (عميل من نفس المنشأة، وإلا 404):
- ملخص السلال حسب الحالة (عدد + إجمالي)، `totalOrders`, `totalSpent`.
- `avgBasket` و`lastVisit` (**يستثنيان الملغاة** ليعكسا الإنفاق الحقيقي).
- آخر 20 سلة.
- **الولاء:** رصيد النقاط (`LoyaltyAccount.pointsBalance`) وقيمته بالريال (× `LoyaltyProgram.pointValue`).
- **الاشتراك الفعّال:** أحدث اشتراك `ACTIVE` غير منتهٍ، مع الخطة.
- **كل الاشتراكات الحالية** (`ACTIVE`/`FROZEN`) مع المتبقّي وحالة السداد لكل باقة.
- العنوان النصّي المفرد (`customer.address`).

**الصلاحية:** طاقم مصادَق (قراءة).

### 5.6 طلبات العميل — `GET /customers/{id}/orders`

سجل سلال العميل الأحدث أولاً (حد 100)، بفلاتر: `status` (RECEIVED/PROCESSING/READY/DELIVERED/CANCELLED)، `paymentStatus` (PAID/PARTIAL/UNPAID/DEFERRED)، `min`/`max` للإجمالي.

**الصلاحية:** طاقم مصادَق (قراءة).

### 5.7 الائتمان / الآجل (creditLimit + credit.config)

يتكوّن نظام الآجل من طرفين:

1. **إعداد الآجل على مستوى المنشأة** — `credit.config:{orgId}` في جدول `Setting`، يديره `ConfigSettingsController` (المجموعة `credit`):
   - `enabled` (boolean، افتراضي false): هل الآجل مفعَّل للمنشأة.
   - `defaultLimit` (float، افتراضي 0، ≤10,000,000): السقف الائتماني الافتراضي.
   - **الصلاحية:** القراءة (`GET /config/credit`) لأي طاقم مصادَق؛ التعديل (`PUT /config/credit`) لـ `requireSuperAdmin` فقط.

2. **السقف الائتماني على مستوى العميل** — `Customer.creditLimit` (float، nullable، ≥0)، يُضبط في إنشاء/تعديل العميل.

**آلية الدفع الآجل نفسها:** عند الدفع بطريقة `DEFERRED` (في `PosController::store` أو `OrderDetailController::storePayment`)، تُضبط حالة الدفع على `DEFERRED` (أو `PAID` إن كان المتبقّي ≤ 0). القيمة المستحقة تظهر لاحقاً في `outstanding` بقائمة العملاء.

> **فجوة مهمة (انظر القسم 9):** `creditLimit` و`credit.config.defaultLimit`/`enabled` **تُخزَّن وتُتحقَّق شكلياً فقط، ولا تُقرأ ولا تُفرَض في أي مسار دفع.** لا يوجد في الكود أي فحص يمنع تجاوز الرصيد الآجل للسقف الائتماني، ولا أي منطق يعطّل زر "آجل" عندما يكون `credit.config.enabled=false`. الإنفاذ الفعلي غائب.

### 5.8 المحفظة كإشارة

`Customer.walletBalance` يُعرَض في قوائم/تفاصيل العميل (إشارة قراءة فقط). كل حركاته (شحن/خصم) تمر حصراً عبر `WalletService` مع قفل `FOR UPDATE`. شحن المحفظة عبر `POST /customers/{id}/wallet/topup` (صلاحية `customers.manage`) وسجل الحركات عبر `GET /customers/{id}/wallet/transactions`. **التفاصيل الكاملة في ملف المدفوعات** — تُذكر هنا للربط فقط.

## 6. قواعد البيزنس (مرقّمة)

1. **النموذج الثلاثي إلزامي:** لا يوجد سعر إلا كـ `Service` (خلية) تحت `Product` تحت `ServiceCategory`. إنشاء منتج بلا أي خلية سعر مرفوض.
2. **أنواع الخدمة ثلاثة فقط:** `WASH` / `IRON` / `WASH_IRON`. أي نوع آخر يُتجاهَل عند إنشاء المنتج.
3. **ترتيب أزرار POS ثابت:** غسيل وكوي (`WASH_IRON`) ← كوي (`IRON`) ← غسيل (`WASH`).
4. **التسعير عند الإنشاء دائماً `PER_PIECE`.**
5. **سعر الاستعجال محسوب:** `express = basePrice + expressSurcharge`؛ لا يُخزَّن سعر استعجال مستقل.
6. **التعطيل لا الحذف:** لا مسار DELETE لتصنيف/منتج/خلية؛ الإزالة عبر `isActive=false` فقط (لأن الطلبات تشير إلى `serviceId`).
7. **إعادة الترتيب = فهرس المصفوفة:** `sortOrder` لكل عنصر يساوي موقعه في مصفوفة `ids` المُرسَلة، داخل معاملة.
8. **إعادة الترتيب معزولة بالمنشأة:** يُرفض الطلب كله (404) إن كان أي معرّف لا يخص المنشأة؛ وللمنتجات: يجب أن تكون تحت التصنيف المذكور أيضاً.
9. **إعادة تسمية المنتج تزامن أسماء خلاياه** (`Service.name`).
10. **رمز المنتج (`code`) له صلاحية مستقلة** `catalog.manageCodes`، منفصلة عن دور المدير.
11. **الإنشاء يذهب لآخر القائمة:** التصنيف/المنتج الجديد يأخذ `sortOrder = max+1` (أو 0 لأول عنصر).
12. **الكتالوج المعروض في POS مصفّى:** تُستبعَد المنتجات بلا خلايا نشطة والتصنيفات بلا منتجات؛ لكن `allCategories` يُظهر كل التصنيفات النشطة (حتى الفارغة) لصفحة الإدارة.
13. **تفرّد هاتف العميل داخل المنشأة فقط:** يجوز تكرار نفس الرقم عبر منشآت مختلفة، لكن ليس داخل المنشأة الواحدة.
14. **طول اسم العميل مقيَّد (2–200):** لأنه يُنسخ حرفياً إلى فاتورة ZATCA وقوالب واتساب.
15. **نوع العميل من ثلاثة:** `REGULAR`/`VIP`/`CORPORATE`.
16. **لا يُحذف عميل له طلبات** (حماية سجل الطلبات).
17. **المستحقّات (`outstanding`) تشمل** الطلبات غير الملغاة ذات حالة `UNPAID`/`PARTIAL`/`DEFERRED`، بمقدار `grandTotal − paidTotal` (لا تنزل تحت صفر).
18. **المتوسط وآخر زيارة يستثنيان الملغاة.**
19. **عنوان افتراضي واحد لكل عميل:** تعيين عنوان كافتراضي يُلغي السابق داخل معاملة واحدة.
20. **عناوين التوصيل ملك العميل:** يديرها العميل عبر البوابة فقط (مقيَّدة بـ `customerId`)، لا طاقم المنشأة.
21. **حركات المحفظة عبر `WalletService` حصراً** مع قفل الصف؛ لا كتابة مباشرة لـ `walletBalance`.
22. **كل عمليات الكتابة معزولة بالمنشأة** (`orgId`)؛ أي مورد من منشأة أخرى → 404.
23. **إعداد الآجل على مستوى المنشأة يعدّله SUPER_ADMIN فقط.**

## 7. الأدوار والصلاحيات لكل عملية

آلية البوابات (من `ResolvesTenant`):
- `assertStaff` — يرفض توكنات العميل/المورد/المسوّق (تحمل orgId لكنها ليست طاقماً)؛ يُستدعى ضمنياً عبر `orgId()`.
- `requireManager` — `SUPER_ADMIN` أو `BRANCH_MANAGER`.
- `requireSuperAdmin` — `SUPER_ADMIN` فقط.
- `requirePermission(key)` — يفحص صلاحيات المستخدم الفعلية (`StaffPermissions::has`)؛ التجاوزات لكل مستخدم تحلّ محل صلاحيات الدور الافتراضية بالكامل.

الصلاحيات الافتراضية للأدوار ذات الصلة (من `OrgUserController::ROLE_PERMISSIONS`):

| الدور | يملك `customers.manage`؟ | يملك `catalog.manageCodes`؟ | مدير (لعمليات الكتالوج)؟ | يعدّل إعداد الآجل؟ |
|---|---|---|---|---|
| `SUPER_ADMIN` | نعم | نعم | نعم | نعم |
| `BRANCH_MANAGER` | نعم | نعم | نعم | لا |
| `CASHIER` | نعم | لا | لا | لا |
| `RECEPTION` | نعم | لا | لا | لا |

ملاحظة: صلاحية `catalog.manage` مُعرَّفة في كتالوج الصلاحيات ("تعديل الكتالوج والأسعار") لكن عمليات كتابة الكتالوج في `CatalogController` تعتمد فعلياً على `requireManager` (الدور) وليس على مفتاح `catalog.manage`. (فجوة — القسم 9.)

## 9. حالات خاصة وفجوات معروفة

1. **السقف الائتماني غير مُنفَّذ:** `Customer.creditLimit` و`credit.config` (`enabled`/`defaultLimit`) يُخزَّنان ويُتحقَّق منهما شكلياً، لكن **لا يُقرآن في أي مسار دفع**. لا يوجد فحص يمنع الآجل من تجاوز السقف، ولا يوجد ربط بين `credit.config.enabled` وإتاحة طريقة `DEFERRED`. الإنفاذ الفعلي متروك للواجهة أو غائب تماماً.
2. **`catalog.manage` معرَّفة لكن غير مستخدمة للبوابة:** كتابة الكتالوج تعتمد على `requireManager` (الدور) لا على مفتاح `catalog.manage`. المفتاح يظهر في كتالوج الصلاحيات لكنه غير فعّال في هذا الكنترولر، ما يعني أن منح/منع `catalog.manage` لموظف لا يغيّر قدرته على تعديل الكتالوج.
3. **لا CRUD لأنواع القطع (`GarmentType`):** لا نقطة نهاية لإنشاء/تعديل أنواع القطع في هذا الـ API؛ تُقرأ فقط لتسمية بنود الفاتورة. إدارتها من نظام Next.js أو seed.
4. **لا CRUD للوحدات (`Unit`) في مجال الكتالوج:** تُدار جزئياً ضمن المخزون فقط.
5. **العميل مطلوب دائماً في POS:** `PosController::store` يشترط `customerId`. لا يوجد في هذا الكود إنشاء تلقائي لـ "عميل كاش/عابر (walk-in)" افتراضي — أي عميل افتراضي للبيع النقدي يجب أن يكون قد أُنشئ مسبقاً (seed/الواجهة) وتُمرَّر معرّفه. (لا يوجد ثابت أو منطق walk-in في الطبقة الخلفية.)
6. **حقلا العنوان مختلفان:** `Customer.address` نصّي حر مفرد (≤500)، بينما `CustomerAddress` كيان منظّم متعدد يديره العميل من البوابة. لا مزامنة بينهما.
7. **تعطيل التصنيف لا يعطّل منتجاته:** تعطيل تصنيف يخفيه من POS (استعلام العرض يشترط `isActive` للتصنيف)، لكن منتجاته تبقى `isActive=true` في قاعدة البيانات؛ لا cascade تعطيل.
8. **`walletBalance` للعرض فقط في هذا المجال:** لا يُكتب من `CustomerController` (غير مدرج في `fillable`)؛ كل تعديل عبر `WalletService`.
9. **حد القوائم ثابت (100) بلا ترقيم صفحات (pagination):** قائمة العملاء وطلبات العميل مقطوعتان عند 100 صفاً دون آلية صفحات، ما قد يخفي بيانات لمنشأة كبيرة.
10. **تعطيل خلية سعر:** لا مسار مباشر لتعطيل خلية `Service` مفردة عبر هذا الـ API؛ التعطيل يتم على مستوى المنتج/التصنيف. تعديل `PUT /catalog/services/{id}` يغيّر السعر فقط لا حالة التفعيل.
